def generate_plan(state, config):
    # 1. 关键守门：如果 plan_status != "unconfirmed"，跳过生成
    if state.get("plan_status", "unconfirmed") != "unconfirmed":
        return {}
    # 2. 调 LLM 生成计划
    agent = Agent(...); agent.set_step_prompt(plan_instructions)
    response = agent.step(current_date, research_topic, research_proposal)
    response = Post.extract_pattern(response, pattern="markdown")
    # 3. 写入 plan + plan_status=unconfirmed + plan_messages
    return {
      "messages":      [AIMessage(response)],
      "plan":           response,
      "plan_status":   "unconfirmed",
      "plan_messages": [AIMessage(response)]
    }

⑤ 后端 · evaluate_plan 路由

def evaluate_plan(state, config):
    if state.get("plan_status","unconfirmed") == "unconfirmed":
        return "awaiting_plan_confirmation"   # ← HITL 中断点
    if not state.get("plan"):
        return "replan"
    last = get_last_user_response(state["messages"])
    if "开始研究" in last or "需求确认" in last:
        return GENERATE_SEARCH_NODE
    # 否则用 LLM 判断
    result = JsonAgent(PlanReflection).step(research_proposal=plan, context=last)
    return GENERATE_SEARCH_NODE if result.satisfy else "replan"

8. HITL 完整步骤拆解（人 / 前端 / 后端 各自的动作）

人 Step 1 在 InputForm 输入研究主题（例：「如何评价 DeepSeek 成立 Harness 团队」），选择 effort/model。 effort: 1/1(低) / 3/3(中) / 5/10(高) — 控制 initial_search_query_count 与 max_research_loops。
前端 Step 2 App.handleSubmit 拼装 thread.submit payload：messages 追加 + plan_status="unconfirmed"。 首次提交时 awaitingPlanConfirmation 初始值 "unconfirmed"；后续提交 = "confirmed"。
后端 Step 3 LangGraph 进入 generate_plan。plan_status=="unconfirmed" → LLM 调 plan_instructions 写 plan。 同时写 messages + plan + plan_messages；plan_status 仍写 "unconfirmed"。
后端 Step 4 evaluate_plan 路由：plan_status=="unconfirmed" → 进入 awaiting_plan_confirmation 节点。 该节点是 lambda：lambda state, config: state，状态不变但停止向下推进。
前端 Step 5 useStream onUpdateEvent 收到 generate_plan 事件：渲染 AiMessageBubble + "initiate research" 按钮。 同时 setAwaitingPlanConfirmation("confirmed") — 让用户下次提交能跳过生成。
人 Step 6 阅读计划，做三个动作之一： (a) 直接点击按钮 → 提交 "需求确认"
(b) 在 InputForm 修改意见 → 提交自由文本（触发 PlanReflection.satisfy=false → replan）
(c) 重新开始 → 刷新页面
后端 Step 7 用户提交触发新一次 thread.submit → 再次进入 generate_plan。 由于 plan_status="confirmed"，节点 return {} 跳过；evaluate_plan 走 generate_query 路径。
后端 Step 8 generate_query → SearchQueryList → Send fan-out 到 web_search × N。 每路 web_search 写 web_search_result + sources_gathered + search_query（追加）。
后端 Step 9 critique 节点：research_loop_count+=1 + Reflection{is_sufficient, knowledge_gap, follow_up_queries}。 route_evaluate 决定继续 Send(web_search) 还是 → final_answer。
后端 Step 10 final_answer：替换短链回原 URL + 入库 unique_sources → emit AIMessage。 前端收到 finalize_answer 事件，把最后一条 AI 消息的活动时间线存档到 historicalActivities。
前端 Step 11 ChatMessagesView 渲染最终答卷 + 复制按钮 + 引用徽章。 用户随时可在 InputForm 继续提问（在 messages 里追加），后端继续走 plan→query→search 循环。

9. HITL 中断机制（为什么是"软中断"？）

本项目不是用 LangGraph 内置的 interrupt 工具，而是用 「空 lambda 节点 + plan_status 状态字段」 实现软中断。下方时序图把"用户两次提交"之间状态机的全部动作一帧一帧摊开：

关键观察：① 不是"硬 interrupt"，而是一个啥也不做的 lambda 节点 + 状态字段守卫； ② generate_plan 节点看到 plan_status 已是 confirmed 就直接 return {}，所以第 2 次进入 LLM 不会被浪费； ③ "需求确认" 关键词是字符串匹配，绕开了 PlanReflection 的 LLM 判定； ④ 前端必须主动维护 await 状态（useState("unconfirmed") + onUpdateEvent 双重保险）。 优势：兼容本地多次提交、不需要 persistent checkpointer； 劣势：如果用户刷新页面或开新 tab，await 状态会丢失，需重新建立。
