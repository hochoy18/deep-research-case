1. awaiting_plan_confirmation 是什么

一句话定义

它是一个 "什么都不做"的占位节点，让 LangGraph StateGraph 在这里停下来，等待前端从浏览器侧发起下一次 thread.submit({...})。整个 HITL 中断机制的核心就是：

  • 节点本体：lambda state, config: state —— 返回 state 本身，不修改任何字段，也不路由到任何下游节点（graph.py:362）。
  • 进入条件：在 evaluate_plan 路由函数里，当 state.get("plan_status", "unconfirmed") == "unconfirmed" 时返回字符串字面量 "awaiting_plan_confirmation"（graph.py:98）。
  • 恢复条件：前端发起新的 thread.submit(...)，把 plan_status 字段以 "confirmed" 提交 → 下一次进入 generate_plan 时该节点因为 plan_status != "unconfirmed" 直接 return {}（graph.py:58-59），图就会再次走到 evaluate_plan，这时走另一条分支。
  • 性质：不是 LangGraph 内置的 interrupt(...)，而是项目自创的"软中断"——图本身从不真正阻塞，只是停在 awaiting_plan_confirmation 上，靠前端推一次新消息来推动它继续。
关键洞见： 整个 HITL 状态机里 没有持久化，plan_status 不是后端存起来的，而是前端每次发起 submit 时重新拼装塞进去的。后端 generate_plan / evaluate_plan 只是"读取 → 判断 → 路由"。所以这个"中断"其实是前端主导、后端顺从的协作模式。

9. 现状、坑与改进方向

9.1 「initiate research」按钮目前是"哑"的

ChatMessagesView.handleStartResearch 内部用了 inputFormRef.current.setInputValue("需求确认") 和 inputFormRef.current.submitInput("需求确认")，但是 InputForm.tsx 既没用 React.forwardRef 也没用 useImperativeHandle，所以这两个方法在 ref 上都是 undefined：

// frontend/src/components/ChatMessagesView.tsx:302-311
const handleStartResearch = () => {
  if (inputFormRef.current && typeof inputFormRef.current.setInputValue === 'function') {
    inputFormRef.current.setInputValue("需求确认");
    setResearchStarted(true);
    if (typeof inputFormRef.current.submitInput === 'function') {
      inputFormRef.current.submitInput("需求确认");
    }
  }
  // ↑ 由于 InputForm 没有暴露这两个方法，整段是 no-op
};

结果：点击按钮后 React 状态 researchStarted 永远不会被置为 true，按钮 label 也不会变；要真正"开始研究"只能自己在 InputForm 里手动输入 "需求确认" 或 "开始研究" 再点探索。

9.2 前端 awaitingPlanConfirmation 是单 bit 状态机

仅有两个值："unconfirmed" / "confirmed"。重新加载页面后会回到初始值。如果用户在 awaiting_plan_confirmation 期间切换 tab 后回来，无法从 UI 区分"是否已经生成过计划"。

9.3 后端 plan_status 没有持久化

LangGraph 的图本身没有用 checkpointer，每次 submit 都是无状态的。完全靠前端记忆 + 每次重提交来"伪造"状态。这对开发期简单可调试，但生产环境若要做"用户离开再回来能恢复"则需要补 PostgreSQL/SqliteSaver。

9.4 plan_messages 写重复

每次 generate_plan 都会 return {"plan_messages": [AIMessage(content=response)]}，由于 add_messages reducer 是按 id 去重的，如果没有显式 id，AIMessage 会被累加——这一点 frontend/src/components/ChatMessagesView.tsx 的"判断最后一条 AI 消息是否含生成计划"逻辑依赖去重后的最新一条。

9.5 PlanReflection.satisfy=false 之后的回路是隐式的

用户输入修改意见 → LLM 判定不满足 → replan 节点把 plan_status="unconfirmed" → 再次进入 generate_plan → 重做计划 → 再次进入 awaiting_plan_confirmation。这一轮回路由 evaluate_plan 拼接完成，用户会看到第二次 "生成计划" 事件，前端需要正确把它再次渲染为"研究计划"分支（带按钮），而不是当成普通 AI 消息。

9.6 改进方向

  • 给 InputForm 加 React.forwardRef + useImperativeHandle({ setInputValue, submitInput })，让按钮真正生效。
  • 把 plan_status 改为更语义化的枚举："drafting" | "awaiting_review" | "approved" | "revising"，方便 UI 区分状态。
  • 考虑加 LangGraph 的 interrupt 工具，把"等待"做成硬中断（需要配 checkpointer）；但会改变当前的"前端拼装、后端读取"模型，需要重新设计调用方。

10. 一句话总结

awaiting_plan_confirmation 本身是一个"什么也不做"的 lambda 节点；它"暂停"图的能力完全来自于 evaluate_plan 路由函数 return "awaiting_plan_confirmation" 这一行——而从该节点"恢复"则完全靠前端在 thread.submit 时把 plan_status 字段从 "unconfirmed" 翻成 "confirmed"，让 generate_plan 的反向短路触发跳过生成。后端不参与状态管理：后端只在每次 submit 时"读"一次字段、"判断"一次路由；状态本身由前端 React 本地 useState 维护 + 每次重新拼接回 payload。

这种设计的本质：把 LangGraph 当成"按调用执行的纯函数管道"，HITL 状态用 React state + URL 不变量表达，graph 本身保持简单（只有 1 个 lambda 节点 + 1 个路由分支 + 1 个状态字段）。
