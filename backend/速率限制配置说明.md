# Web 搜索速率限制配置指南

## 概述

本系统实现了智能速率限制器，用于控制 Web 搜索 API 的请求频率，避免触发 429 (Too Many Requests) 错误。

## 核心机制

### 1. 令牌桶算法
- **实现位置**: `backend/src/agent/base_agent.py` - `RateLimiter` 类
- **工作原理**: 在每次 API 请求前检查距离上次请求的时间间隔，如果间隔太短则自动等待
- **线程安全**: 使用 `threading.Lock` 确保并发环境下的正确性

### 2. 全局单例模式
- 所有 `WebSearchAgent` 实例共享同一个速率限制器
- 无论有多少并发搜索请求，都会被统一调度

## 配置参数

### 环境变量配置（`.env` 文件）

```bash
# Web 搜索最大 QPS（每秒请求数）
# 建议设置为 API 提供商允许值的 80%，留有余量
# 默认值: 12 QPS
WEB_SEARCH_MAX_QPS=12

# 初始搜索查询数量
# 决定第一次生成的搜索查询数量，直接影响首次并发数
# 默认值: 3
NUMBER_OF_INITIAL_QUERIES=3

# 最大研究循环次数
# 控制整个研究过程的迭代次数
# 默认值: 2
MAX_RESEARCH_LOOPS=2
```

## 配置建议

### 场景 1: API 限制为 15 QPS
```bash
WEB_SEARCH_MAX_QPS=12        # 15 * 0.8 = 12，留 20% 余量
NUMBER_OF_INITIAL_QUERIES=3  # 首次并发 3 个请求
MAX_RESEARCH_LOOPS=2         # 最多 2 轮迭代
```

### 场景 2: API 限制为 10 QPS
```bash
WEB_SEARCH_MAX_QPS=8         # 10 * 0.8 = 8
NUMBER_OF_INITIAL_QUERIES=2  # 降低首次并发数
MAX_RESEARCH_LOOPS=2
```

### 场景 3: API 限制为 5 QPS（严格限制）
```bash
WEB_SEARCH_MAX_QPS=4         # 5 * 0.8 = 4
NUMBER_OF_INITIAL_QUERIES=2
MAX_RESEARCH_LOOPS=1         # 减少迭代次数
```

### 场景 4: 高配额 API（50+ QPS）
```bash
WEB_SEARCH_MAX_QPS=40        # 50 * 0.8 = 40
NUMBER_OF_INITIAL_QUERIES=5  # 可以提高并发数
MAX_RESEARCH_LOOPS=3         # 增加迭代深度
```

## 工作原理示例

假设配置 `WEB_SEARCH_MAX_QPS=12`：

1. **最小请求间隔** = 1 / 12 ≈ 0.083 秒（83 毫秒）

2. **并发请求处理流程**：
   ```
   时间线:
   T=0.000s  → 请求1 立即发送
   T=0.050s  → 请求2 到达，等待 33ms
   T=0.083s  → 请求2 发送
   T=0.100s  → 请求3 到达，等待 67ms
   T=0.166s  → 请求3 发送
   ...
   ```

3. **实际效果**：
   - 即使 LangGraph 并行发起 5 个搜索请求
   - 速率限制器会将它们分散到 5 × 0.083 = 0.415 秒内发送
   - 平均 QPS 始终 ≤ 12

## 常见问题

### Q1: 为什么默认值是 12 而不是 15？
**A**: 留有余量是最佳实践。如果 API 限制是 15 QPS，设置为 12 可以：
- 应对瞬时流量峰值
- 为重试请求预留空间
- 避免因时钟不同步导致的超限

### Q2: 如何确认当前配置是否合适？
**A**: 观察日志中的 429 错误频率：
- **频繁出现 429** → 降低 `WEB_SEARCH_MAX_QPS`
- **从未出现 429 且响应快** → 可以适当提高
- **偶尔出现 429** → 当前配置合理

### Q3: 速率限制会影响性能吗？
**A**: 
- **轻微影响**：请求会被均匀分散，总耗时略微增加
- **显著改善**：避免 429 错误导致的长时间重试（5-15 秒）
- **总体收益**：稳定性提升 > 速度损失

### Q4: 多个用户同时使用会怎样？
**A**: 
- 全局单例限制器会统一管理所有请求
- 无论多少用户，总 QPS 都不会超过设定值
- 如果需要每用户独立限流，需要修改实现

## 高级配置

### 动态调整 QPS

可以在运行时重新初始化限制器：

```python
from agent.base_agent import get_web_search_rate_limiter, RateLimiter

# 重置全局限制器（不推荐在生产环境使用）
import agent.base_agent as base_agent
base_agent._web_search_rate_limiter = RateLimiter(max_qps=10)
```

### 针对不同 API 使用不同限流器

如果需要为不同的 MCP 工具设置独立的限流：

```python
# 创建专用限流器
search_limiter = RateLimiter(max_qps=12)
other_limiter = RateLimiter(max_qps=5)

# 在对应的 Agent 中使用
search_limiter.acquire()  # 搜索请求
other_limiter.acquire()   # 其他请求
```

## 故障排除

### 问题 1: 仍然频繁出现 429 错误

**解决方案**：
1. 降低 `WEB_SEARCH_MAX_QPS` 到 8 或更低
2. 减少 `NUMBER_OF_INITIAL_QUERIES` 到 2
3. 检查是否有其他应用共用同一 API Key
4. 联系 API 提供商确认实际配额

### 问题 2: 请求速度过慢

**解决方案**：
1. 确认 API 的实际 QPS 限制
2. 适当提高 `WEB_SEARCH_MAX_QPS`
3. 检查网络延迟是否正常
4. 查看日志中的等待时间是否合理

### 问题 3: 限流器未生效

**解决方案**：
1. 检查 `.env` 文件是否正确加载
2. 确认环境变量名称拼写正确
3. 重启后端服务使配置生效
4. 查看初始化日志确认 QPS 值

## 技术细节

### 线程安全性
- 使用 `threading.Lock` 保护共享状态
- 适用于 LangGraph 的并行执行模型
- 支持多进程环境（每个进程独立实例）

### 精度保证
- 基于 `time.time()` 高精度计时
- 最小间隔计算：`1.0 / max_qps`
- 实际等待时间记录并输出到日志

### 容错机制
- 即使限流器失败，仍有 429 重试机制作为后备
- 递增等待策略：5s → 10s → 15s
- 最多重试 3 次后返回 None

## 总结

通过配置 `WEB_SEARCH_MAX_QPS`，您可以：
- ✅ 精确控制 API 请求频率
- ✅ 避免触发 429 错误
- ✅ 平衡速度与稳定性
- ✅ 适应不同的 API 配额

**推荐配置公式**：
```
WEB_SEARCH_MAX_QPS = API限制QPS × 0.8
```

这样既能充分利用配额，又能保持稳定运行。
