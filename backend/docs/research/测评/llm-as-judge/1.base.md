当然。**LLM-as-a-Judge（让大语言模型充当评审器）**已经是 LLM 应用评测里非常重要的一套方法。它本质上是在解决：

> **当模型输出不是一个容易用“准确/错误”衡量的答案时，如何系统、自动、规模化地判断这个答案好不好？**

例如：

* “这封邮件写得专业吗？”
* “这个 RAG 回答有没有忠实于检索资料？”
* “两个模型谁的回答更好？”
* “这个 Agent 有没有正确完成任务？”
* “生成的代码是否满足需求？”
* “回答是否存在幻觉、废话、偏见？”

下面我从**概念 → 数学形式 → Judge 设计 → 评测协议 → 偏差 → 校准 → 实战框架 → 高级方法**完整讲一遍。

---

# 1. LLM-as-a-Judge 到底是什么？

最简单的形式：

```text
User Query
    ↓
Candidate Answer
    ↓
┌─────────────────────┐
│      LLM Judge      │
│                     │
│  Criteria / Rubric  │
│  Reference Answer   │
│  Context            │
└─────────────────────┘
    ↓
Score / Preference / Critique
```

例如我们有：

**问题**

> 什么是 Transformer？

**模型 A**

> Transformer 是一种基于 CNN 的序列模型……

**模型 B**

> Transformer 是一种主要依赖 self-attention 机制的神经网络架构……

让另一个 LLM 来判断：

```text
Judge:
A = 3/5
B = 5/5
Winner = B
Reason = B 对 Transformer 的核心机制描述更准确……
```

这就是最基本的 **LLM-as-a-Judge**。

---

# 2. 为什么需要 LLM Judge？

传统 NLP evaluation 有很多指标：

| 任务 | 传统指标             |
| -- | ---------------- |
| 分类 | Accuracy / F1    |
| 翻译 | BLEU             |
| 摘要 | ROUGE            |
| 检索 | Recall / NDCG    |
| QA | Exact Match / F1 |

但生成式 AI 的问题是：

> **“正确”不一定等于“好”。**

比如用户：

> 帮我写一封拒绝面试的邮件。

下面两个答案可能都正确：

**A**

> Thank you for your email. I am unable to attend.

**B**

> Thank you very much for reaching out and for the opportunity to interview. After careful consideration, I’ve decided to withdraw from the process at this time. I sincerely appreciate your time and consideration.

如果只做字符串匹配：

```text
A ≠ B
```

但人类显然可以判断：

```text
B > A
```

于是我们需要一个更接近人类判断的 evaluator。

而 LLM 恰好具有：

* 语言理解能力
* 上下文理解能力
* 推理能力
* instruction following
* 能理解复杂 rubric

所以自然可以：

> **让 LLM 模拟 human evaluator。**

---

# 3. LLM Judge 的三个主要范式

实际上最重要的是这三个。

## 3.1 Pointwise：单答案打分

给 Judge 一个答案，让它评分。

```text
Question
Answer
Rubric
   ↓
Judge
   ↓
Score = 4/5
```

例如：

```text
Criteria:

1. Correctness
2. Relevance
3. Completeness
4. Clarity

Score each from 1 to 5.
```

最终：

```json
{
  "correctness": 5,
  "relevance": 4,
  "completeness": 4,
  "clarity": 5
}
```

### 优点

简单，而且可以同时得到多个维度。

### 缺点

**分数本身不一定可靠。**

例如：

```text
Model A = 4.1
Model B = 4.2
```

不能轻易解释成：

> B 一定比 A 好很多。

尤其 LLM 对 absolute score 的 calibration 通常不稳定。

---

# 4. Pairwise：两个答案比较

这通常是 LLM Judge 最有用的方式之一。

给：

```text
Question

Answer A

Answer B
```

要求：

> 哪一个更好？

输出：

```text
A / B / Tie
```

例如：

```json
{
  "winner": "B",
  "reason": "B provides a more accurate and complete explanation..."
}
```

这叫：

> **Pairwise Preference Evaluation**

它背后的思想很重要：

相比于问：

> “这个答案到底是 82 分还是 87 分？”

人类通常更擅长：

> “A 和 B 哪一个更好？”

这也是为什么很多 LLM evaluation benchmark 会采用 pairwise comparison。

---

# 5. Listwise：一次比较多个答案

再进一步：

```text
A
B
C
D
```

Judge：

```text
Rank:

1. C
2. B
3. D
4. A
```

这叫：

> **Listwise evaluation**

适合：

* 多模型 benchmark
* 多个 prompt 比较
* candidate ranking
* search / recommendation

但它也更容易产生：

> **position bias / ranking instability**

所以实际使用时要比较谨慎。

---

# 6. Judge 最核心的东西：Rubric

很多人做 LLM-as-a-Judge 最大的问题不是模型选错了。

而是：

> **根本没有定义清楚“什么叫好”。**

比如：

> 请评价这个答案。

这是一个非常差的 evaluator prompt。

更好的方式是定义：

```text
Evaluate the answer on:

1. Correctness
   - Is the answer factually accurate?
   - Are there any logical errors?

2. Relevance
   - Does it directly address the user's question?
   - Does it avoid irrelevant information?

3. Completeness
   - Does it cover the important aspects?

4. Clarity
   - Is it easy to understand?

5. Groundedness
   - Is every factual claim supported by the provided context?
```

这就是 **evaluation rubric**。

---

# 7. Rubric 应该怎么设计？

一个好的 rubric 至少包含四个东西：

```text
Dimension
Definition
Positive criteria
Negative criteria
```

例如：

### Correctness

```text
5 = Completely correct, no substantive errors
4 = Mostly correct, minor inaccuracies
3 = Partially correct, some important omissions
2 = Significant errors
1 = Fundamentally incorrect
```

注意：

**一定要定义 score anchor。**

不要：

```text
1-5 分
```

然后什么都不解释。

应该：

```text
5 → excellent
4 → good
3 → acceptable
2 → poor
1 → unacceptable
```

更进一步：

```text
5:
No factual errors and fully addresses the question.

4:
Mostly correct, with at most minor errors.

3:
Generally useful but contains one or more substantive omissions.

2:
Contains significant factual or reasoning errors.

1:
Fundamentally wrong or irrelevant.
```

这样 Judge 的一致性通常会明显提升。

# 8. Pointwise Judge 的标准 Prompt

一个比较标准的结构：

```text
You are an expert evaluator.

Your task is to evaluate the quality of the candidate answer.

# User Query
{query}

# Candidate Answer
{answer}

# Evaluation Criteria

## Correctness
...

## Relevance
...

## Completeness
...

## Clarity
...

# Instructions

Evaluate the answer according to the criteria above.

For each criterion:
1. Assign a score from 1 to 5.
2. Provide a concise justification.

Finally, provide an overall score.

Return the result in JSON format.
```

例如：

```json
{
  "correctness": {
    "score": 5,
    "reason": "..."
  },
  "relevance": {
    "score": 4,
    "reason": "..."
  },
  "completeness": {
    "score": 4,
    "reason": "..."
  },
  "clarity": {
    "score": 5,
    "reason": "..."
  },
  "overall": 4.5
}
```

# 9. RAG 场景的 Judge

RAG 是 LLM Judge 特别有价值的场景。

因为 RAG 不只是：

> 答案好不好？

还要判断：

> **答案是否被检索到的证据支持？**

因此通常拆成两个维度。

## Faithfulness / Groundedness

```text
Context:
{retrieved_documents}

Answer:
{answer}
```

Judge：

> Are the claims in the answer supported by the provided context?

例如：

Context：

> Apple released the iPhone 15 in September 2023.

Answer：

> Apple released the iPhone 15 in September 2023 and it used a titanium frame.

如果 context 没有 titanium：

```text
Faithfulness = low
```

即使：

```text
“titanium frame”
```

实际上是真的。

这点非常重要：

> **RAG faithfulness ≠ factual correctness**

---

# 10. Correctness vs Faithfulness

这是做 LLM evaluation 必须搞清楚的区别。

假设：

```text
Context:
Paris is the capital of France.
```

Answer：

> Paris is the capital of France and has a population of 2.1 million.

可能：

```text
Correctness = high
Faithfulness = low
```

因为第二个 claim 没有被 context 支持。

反过来：

```text
Context:
Paris is the capital of France.
```

Answer：

> Paris is the capital of Germany.

那么：

```text
Correctness = low
Faithfulness = low
```

所以 RAG evaluation 通常至少要：

```text
Retrieval Quality
       ↓
Context Relevance
       ↓
Faithfulness
       ↓
Answer Correctness
       ↓
Answer Relevance
```

---

# 11. 一个更严谨的 RAG Evaluation Pipeline

可以设计成：

```text
                    ┌──────────────┐
                    │    Query     │
                    └──────┬───────┘
                           ↓
                    ┌──────────────┐
                    │   Retriever  │
                    └──────┬───────┘
                           ↓
                     Retrieved Docs
                           │
              ┌────────────┴────────────┐
              ↓                         ↓
       Retrieval Judge             Generation
              │                         │
              ↓                         ↓
      Context Relevance              Answer
                                        │
                                        ↓
                              ┌─────────────────┐
                              │   LLM Judge     │
                              └─────────────────┘
                                ↓       ↓
                          Faithfulness Correctness
```

这比单纯：

```text
Question → Answer → Score
```

强很多。

---

# 12. LLM Judge 的真正难点：Judge 不是“上帝”

这是理解整个 methodology 最重要的一点：

> **LLM Judge 自己也是一个有偏差的模型。**

因此：

```text
LLM
 ↓
产生答案

LLM
 ↓
评价答案
```

可能产生：

> **model-induced evaluation bias**

所以不能简单认为：

```text
Judge score = ground truth
```

正确的思维应该是：

```text
Human Judgment
      ↑
  calibration
      ↑
LLM Judge
      ↑
evaluation protocol
```

---

# 13. 常见 Judge Bias

这里是 LLM-as-a-Judge 最核心的研究问题。

## 13.1 Position Bias

例如：

```text
Answer A
Answer B
```

Judge 可能偏向 A。

换成：

```text
Answer B
Answer A
```

结果却变成 B。

所以 pairwise evaluation 最基本的办法：

> **Swap the order。**

即：

```text
Trial 1:
A vs B

Trial 2:
B vs A
```

如果：

```text
P(A wins | A first)
≈
P(A wins | B first)
```

说明 position bias 较小。

---

# 14. 位置交换是一个非常重要的技巧

假设：

```text
Judge 1:
A > B

Judge 2:
B > A
```

那怎么办？

可以定义：

```text
Agreement:
same winner → 1
different winner → 0
```

然后：

```text
Position consistency
=
# consistent judgments
/
# total pairs
```

例如：

100 对答案：

```text
87 对一致
13 对不一致

Consistency = 87%
```

这比单次 judge 更可信。

---

# 15. 另一个大问题：Verbosity Bias

LLM 很容易喜欢：

> 写得更多的答案。

例如：

**A**

> Transformer 使用 self-attention。

**B**

> Transformer 是一种革命性的深度学习架构……
> 它通过 self-attention……
> 此外，它还具有……
> 从历史角度来看……
> 总而言之……

Judge 很可能：

```text
B > A
```

即使：

```text
A = perfectly sufficient
B = verbose
```

这叫：

> **verbosity bias**

解决方式之一：

在 rubric 中明确：

```text
Do not reward an answer merely for being longer.
Penalize unnecessary verbosity when it does not add useful information.
```

---

# 16. Self-preference Bias

如果：

```text
Judge = GPT-X
Candidate = GPT-X
```

可能出现：

> Judge 更喜欢自己模型生成的答案。

例如：

```text
GPT-X Judge:

GPT-X answer = 8.9
Model Y = 8.2
```

这可能是真的，也可能是：

> **self-preference bias**

所以 benchmark 最好：

```text
Judge model ≠ candidate model
```

或者至少测试：

```text
Judge A
Judge B
Judge C
```

看结论是否稳定。

---

# 17. Style Bias

Judge 可能喜欢某种表达方式。

例如：

```text
Answer A:
严谨、简洁

Answer B:
复杂、学术、术语很多
```

如果 rubric 没定义清楚：

```text
Judge ≈ “更像专家的语言” = 更好
```

这不一定成立。

所以：

> **把 style 与 substance 分开。**

例如：

```text
Correctness
Relevance
Completeness
Clarity
Style
```

不要让 style 偷偷影响 correctness。

---

# 18. Position Bias + Verbosity Bias + Self Preference

所以一个成熟的 evaluation pipeline 通常不会：

```text
run judge once
→ trust score
```

而是：

```text
                    ┌─ order A/B
                    │
Candidate Answers ──┼─ order B/A
                    │
                    ├─ Judge Model 1
                    │
                    ├─ Judge Model 2
                    │
                    └─ repeated trials
                             ↓
                         Aggregate
                             ↓
                       Final Score
```

---

# 19. Judge 输出应该包含 Reason 吗？

通常建议：

```text
Score
+
Evidence / Rationale
```

例如：

```json
{
  "winner": "B",
  "reason": "B directly answers the question and correctly explains..."
}
```

原因不是为了让用户看。

而是为了：

> **debug evaluator。**

如果 Judge 说：

```text
B wins because B mentions the moon.
```

但问题根本没问 moon：

你就知道：

> Judge 本身有问题。

---

# 20. 但不要盲目信任 Chain-of-Thought

这里要区分：

```text
Evaluation rationale
```

和

```text
private chain-of-thought
```

实际系统通常需要的是：

> **concise evidence-based justification**

例如：

```text
Reason:
Answer B correctly identifies X and avoids the factual error present in A.
```

而不是要求 Judge 展示非常长的内部推理过程。

---

# 21. 更好的方法：Claim-level Evaluation

尤其是 RAG，非常推荐。

先把答案拆成 claims：

```text
Answer:

1. Transformer uses self-attention.
2. It was introduced in 2017.
3. It completely replaced RNNs.
```

Judge 分别判断：

```text
Claim 1 → supported
Claim 2 → supported
Claim 3 → unsupported
```

于是：

```text
Faithfulness
=
supported claims / total claims
```

例如：

```text
2 / 3 = 66.7%
```

这比让 Judge 一句话：

> “这个回答大概 4 分。”

更可解释。

---

# 22. 可以把 Evaluation Formalize

假设：

```text
q = query
a = answer
c = context
r = rubric
J = judge model
```

那么：

### Pointwise

$$
s = J(q,a,c,r)
$$

得到：

$$
s \in [1,5]
$$

---

### Pairwise

$$
p = J(q,a_1,a_2,r)
$$

其中：

$$
p \in \{A,B,Tie\}
$$

---

### Claim-level

答案：

$$
a = \{claim_1,\dots,claim_n\}
$$

Judge：

$$
z_i = J(claim_i,c)
$$

其中：

$$
z_i \in \{0,1\}
$$

那么：

$$
Faithfulness =
\frac{\sum_i z_i}{n}
$$

---

# 23. 从 Pairwise Preference 得到模型排名

如果我们有：

```text
A beats B
B beats C
A beats C
```

就可以构建 preference matrix：

|   |  A |  B |  C |
| - | -: | -: | -: |
| A |  — |  1 |  1 |
| B |  0 |  — |  1 |
| C |  0 |  0 |  — |

然后计算：

```text
Win Rate
```

例如：

$$
WinRate(A)=\frac{wins_A}{comparisons_A}
$$

更复杂一点，可以使用：

* Bradley-Terry model
* Elo
* TrueSkill
* Plackett-Luce

把 pairwise preference 转成 latent ability：

$$
P(A>B)=
\frac{e^{\theta_A}}
{e^{\theta_A}+e^{\theta_B}}
$$

其中：

$$
\theta_A
$$

可以理解成模型 A 的 latent quality。

---

# 24. 为什么 Bradley-Terry 很有用？

假设你有 10 个模型：

```text
A B C D E F G H I J
```

不需要：

```text
每个模型都跟所有模型比较很多次
```

可以收集 pairwise：

```text
A vs B
A vs C
B vs D
...
```

然后拟合：

$$
\theta_1,\theta_2,...,\theta_n
$$

最终得到：

```text
Ranking
```

这其实是非常漂亮的一套方法：

```text
LLM Judge
   ↓
Pairwise preferences
   ↓
Statistical model
   ↓
Latent quality
   ↓
Ranking
```

而不是直接把 LLM 输出的：

```text
8.7 / 10
```

当成绝对真理。

---

# 25. Human Evaluation 仍然非常重要

LLM Judge 最好的定位不是：

> 替代人类。

而是：

> **扩展人类评测能力。**

典型架构：

```text
               Human Evaluation
                      ↓
                 Gold Dataset
                      ↓
                Calibrate Judge
                      ↓
             ┌─────────────────┐
             │   LLM Judge     │
             └─────────────────┘
                      ↓
              Large-scale eval
```

也就是说：

**Human = calibration / ground truth**

**LLM = scale**

---

# 26. 怎么验证 Judge 靠不靠谱？

这是整个 methodology 最关键的实验。

准备一批：

```text
N human-labeled examples
```

例如：

```text
1000 samples
```

Human：

```text
A > B
```

LLM Judge：

```text
A > B
```

然后计算：

### Agreement

$$
Agreement =
\frac{\#correct}{N}
$$

例如：

```text
Human vs Judge agreement = 87%
```

但还可以更严谨。

---

# 27. Cohen's Kappa

如果是 categorical judgment：

```text
A wins
B wins
Tie
```

可以计算：

$$
\kappa =
\frac{p_o-p_e}{1-p_e}
$$

其中：

* \(p_o\)：observed agreement
* \(p_e\)：chance agreement

为什么不用简单 accuracy？

因为：

> 两个 evaluator 即使随机，也可能偶尔选一样。

Kappa 会修正这种情况。

---

# 28. Spearman / Kendall

如果 Judge 输出 ranking：

```text
Human:

A > C > B > D

Judge:

A > B > C > D
```

可以使用：

### Spearman correlation

$$
\rho
$$

或者：

### Kendall's tau

$$
\tau
$$

衡量：

> Judge ranking 和 human ranking 到底有多一致。

---

# 29. Judge Calibration

如果发现：

```text
Human:
A = 4.0
B = 3.5
```

而 Judge：

```text
A = 5
B = 4
```

这不一定代表 ranking 错。

但说明：

> **absolute score calibration 不好。**

可以进行 calibration。

例如：

```text
Human score
      ↑
      │        /
      │      /
      │    /
      │  /
      └────────→
        Judge score
```

用：

* linear calibration
* isotonic regression
* Platt-style calibration

等方式把：

```text
Judge score → calibrated human-like score
```

---

# 30. 为什么 pairwise 往往比 absolute score 更可靠？

因为：

### Absolute

```text
“这个答案值 83 分吗？”
```

要求 Judge 建立稳定的内部尺度。

这是困难的。

### Pairwise

```text
“A 和 B 哪一个更好？”
```

是相对判断。

通常更容易。

所以：

> **如果你的目标是比较模型，优先考虑 pairwise。**

如果目标是：

> 判断某一个答案是否达到标准。

则：

> pointwise rubric 更合适。

---

# 31. 一个非常实用的 Judge Design

如果让我设计一个生产级 evaluator，我通常会这样：

```text
                 Query
                   │
                   ↓
             Candidate Answer
                   │
                   ↓
        ┌─────────────────────┐
        │  Rule-based checks  │
        └──────────┬──────────┘
                   ↓
        ┌─────────────────────┐
        │    LLM Judge        │
        │                     │
        │ correctness         │
        │ relevance           │
        │ completeness        │
        │ groundedness        │
        └──────────┬──────────┘
                   ↓
          structured JSON
                   ↓
        ┌─────────────────────┐
        │ aggregation         │
        └──────────┬──────────┘
                   ↓
               final score
```

重点：

> **不要让 LLM Judge 做所有事情。**

能用 deterministic rule 判断的：

```text
regex
exact match
JSON validity
schema
SQL execution
unit tests
citation existence
```

就不要浪费 LLM。

# 32. Hybrid Evaluation 是更成熟的做法

例如代码生成：

```text
                 Code Answer
                      │
          ┌───────────┴───────────┐
          ↓                       ↓
     Unit Tests               LLM Judge
          ↓                       ↓
     Functional              Code Quality
     Correctness             Explanation
          │                       │
          └───────────┬───────────┘
                      ↓
                Final Evaluation
```

例如：

```text
Functional correctness = 70%
Code quality = 20%
Explanation = 10%
```

这样远比：

> “让 GPT 给代码打分”

可靠。

---

# 33. Judge Ensemble

一个更高级的办法：

```text
Judge A
Judge B
Judge C
   ↓
Aggregation
```

比如：

```text
GPT
Claude
Gemini
```

分别判断：

```text
A > B?
```

结果：

```text
Judge 1 → A
Judge 2 → A
Judge 3 → B
```

最终：

```text
A wins 2:1
```

这可以降低单个 Judge 的 idiosyncratic bias。

但注意：

> **多个 Judge 不代表一定 unbiased。**

如果三个模型都有同样的 verbosity bias：

```text
A → verbose
B → concise
```

三个都会偏 A。

所以 ensemble 解决的是：

> variance

不一定解决：

> systematic bias

---

# 34. Judge Prompt 还可以加入 Reference Answer

有：

```text
Question
Reference Answer
Candidate Answer
```

Judge：

> Compare candidate with reference.

这通常比：

```text
Question
Candidate
```

更稳定。

但 Reference 也可能带来问题。

比如 reference：

```text
A very specific expected wording
```

Candidate：

```text
different but equally correct
```

Judge 可能认为：

```text
not matching reference = bad
```

所以应该强调：

> **Reference is a correctness aid, not a requirement to match wording.**

---

# 35. Reference-free Judge

也可以：

```text
Question
Candidate Answer
```

让 Judge 自己判断。

优点：

* 不需要人工 reference
* 可规模化

缺点：

* Judge 自己可能不知道正确答案
* factual error 更难判断
* 容易出现 hallucinated evaluation

所以：

> factual / technical benchmark 最好提供 reference、context 或 executable ground truth。

---

# 36. 对事实性问题，Judge 本身也需要 Evidence

例如：

> 谁获得了 2026 年诺贝尔物理学奖？

如果 Judge 不联网、没有 reference：

```text
Question
Answer
```

然后：

```text
Judge: Looks correct.
```

这没有多大意义。

更好的：

```text
Question
Gold / trusted source
Candidate
```

然后 Judge 判断：

```text
Does candidate agree with evidence?
```

---

# 37. Evaluation Data 的设计比 Judge 模型本身更重要

这是一个很容易被忽略的点。

假设：

```text
10000 个简单问题
```

Judge accuracy：

```text
95%
```

看起来很棒。

但是生产环境：

```text
复杂问题
边界情况
adversarial queries
long context
multilingual
ambiguous instructions
```

Judge 可能直接掉到：

```text
70%
```

所以 evaluation set 应该覆盖：

```text
Easy
Medium
Hard
Ambiguous
Adversarial
Long-context
Failure cases
```

---

# 38. Hard Negative 非常重要

如果你测试：

```text
明显正确
vs
明显错误
```

任何 Judge 都很好用。

真正有价值的是：

```text
A = subtle error
B = verbose but slightly wrong
```

或者：

```text
A = concise and correct
B = detailed and mostly correct
```

这类：

> **close-call examples**

才能真正检验 Judge。

# 39. 一个成熟的 Dataset Schema

例如：

```json
{
  "id": "123",
  "query": "...",
  "context": ["...", "..."],
  "reference": "...",
  "answer_a": "...",
  "answer_b": "...",
  "human_winner": "A",
  "difficulty": "hard",
  "tags": [
    "factuality",
    "long_context"
  ]
}
```

然后：

```text
Judge
   ↓
prediction
   ↓
compare human_winner
```

形成 evaluator benchmark。

---

# 40. 最好不要只看平均分

假设：

```text
Model A:
average = 4.2

Model B:
average = 4.3
```

很难知道区别。

应该同时看：

```text
Overall
Correctness
Relevance
Completeness
Faithfulness
Safety
Verbosity
```

以及：

```text
95% CI
```

---

# 41. Statistical Significance

假设：

```text
A wins 53%
B wins 47%
```

不能马上说：

> A 比 B 好。

可能只是 sampling noise。

可以使用：

* bootstrap confidence interval
* permutation test
* paired tests
* binomial test

例如 bootstrap：

```text
10000 bootstrap samples
```

得到：

```text
A win rate:
53.0%
95% CI:
50.8% – 55.2%
```

如果 CI 大幅覆盖 50%，结论就不稳。

---

# 42. Pairwise evaluation 最好使用 matched samples

不要：

```text
A 在问题集合 X
B 在问题集合 Y
```

然后比较平均分。

应该：

```text
Question 1:
A vs B

Question 2:
A vs B

Question 3:
A vs B
```

因为每道题是自己的 control。

这样统计效率更高。

# 43. 一个完整的实验 Protocol

如果你要做论文或者正式 benchmark，可以这样：

### Step 1：定义 task

```text
QA / RAG / Agent / Coding / Writing
```

### Step 2：定义 rubric

```text
Correctness
Relevance
Completeness
...
```

### Step 3：建立 human-labeled calibration set

例如：

```text
500 samples
```

### Step 4：测试多个 Judge

```text
Judge A
Judge B
Judge C
```

### Step 5：测试 bias

```text
Position swap
Answer length
Self preference
Formatting
```

### Step 6：比较 human agreement

```text
Accuracy
Kappa
Spearman
Kendall
```

### Step 7：选择 / calibrate Judge

### Step 8：大规模 evaluation

```text
100k samples
```

### Step 9：confidence interval

### Step 10：failure analysis

最终得到：

```text
Model Quality
+
Judge Reliability
```

这才是比较完整的 methodology。

# 44. Agent 场景会更复杂

比如 Agent 要完成：

> 订一张去东京的机票。

你不能只看最终文字。

需要 evaluation trajectory：

```text
Task
 ↓
Planning
 ↓
Tool call
 ↓
Observation
 ↓
Tool call
 ↓
...
 ↓
Final result
```

Judge 可以判断：

```text
1. Task success
2. Tool correctness
3. Planning quality
4. Error recovery
5. Efficiency
6. Safety
```

例如：

```text
Task Success = 1
Tool Correctness = 0.9
Efficiency = 0.7
```

所以 Agent evaluation 更接近：

> **trajectory-level evaluation**

而不是单纯：

> answer-level evaluation。

---

# 45. 一个重要概念：Outcome vs Process

Agent 可以：

```text
过程很糟
最后成功
```

也可以：

```text
过程很好
最后失败
```

所以：

### Outcome evaluation

> 最终任务完成了吗？

### Process evaluation

> 它是怎么完成的？

二者应该分开。

例如：

$$
Score =
0.7 \times Outcome
+
0.3 \times Process
$$

具体权重取决于任务。

# 46. LLM Judge 的适用场景

特别适合：

### 高适用

* Writing quality
* Conversational quality
* RAG answer quality
* Helpfulness
* Reasoning quality
* Summarization
* Translation quality
* Agent trajectories
* Safety/style evaluation

### 中等适用

* factual QA
* coding quality
* mathematical reasoning

这些最好结合：

```text
ground truth / execution
```

### 不适合单独依赖

* exact numerical correctness
* code execution correctness
* security vulnerabilities
* legal/medical high-stakes factual verification

这些最好：

> deterministic evaluator + expert review + LLM Judge

# 47. 一个很重要的原则

可以把它总结成：

> **Use LLMs to evaluate what is difficult to specify, but use deterministic methods whenever the criterion can be objectively executed.**

比如：

### “JSON 格式对不对？”

不要 LLM Judge。

直接：

```python
json.loads()
```

### “代码能不能运行？”

不要只问 LLM。

直接：

```text
run tests
```

### “有没有完成用户任务？”

可以：

```text
environment state
+
LLM Judge
```

### “写得是否自然？”

LLM Judge 非常合适。

# 48. 最推荐的 Evaluation Architecture

如果你要搭建一个真正能用于生产的 LLM evaluation system，我会推荐：

```text
                    ┌─────────────┐
                    │ Test Dataset│
                    └──────┬──────┘
                           ↓
                    ┌─────────────┐
                    │   Model     │
                    └──────┬──────┘
                           ↓
                       Outputs
                           │
             ┌─────────────┼─────────────┐
             ↓             ↓             ↓
       Deterministic   LLM Judge    Human Sample
          Eval             │             │
             │             │             │
             └─────────────┼─────────────┘
                           ↓
                       Aggregate
                           ↓
                  Statistical Analysis
                           ↓
                     Error Analysis
                           ↓
                    Model Comparison
```

核心思想：

**LLM Judge 不是整个 evaluation system。**

它只是其中一个 evaluator。

# 49. 最容易踩的 10 个坑

| 坑                        | 问题                      |
| ------------------------ | ----------------------- |
| 1. Judge 一次就相信           | variance 很大             |
| 2. 没有 rubric             | 标准漂移                    |
| 3. 只看 absolute score     | calibration 差           |
| 4. 不做 position swap      | position bias           |
| 5. 不控制答案长度               | verbosity bias          |
| 6. Judge 和 candidate 同模型 | self-preference         |
| 7. 没 human calibration   | 不知道 Judge 是否靠谱          |
| 8. 只看平均分                 | 忽略 uncertainty          |
| 9. LLM 判断一切              | 能 deterministic 就不要 LLM |
| 10. 只测试简单数据              | benchmark 失真            |

## 一句话总结

**LLM-as-a-Judge 并不是“找一个更强的 LLM 给答案打分”，而是一套完整的 measurement methodology：**

$$
\boxed{
\text{Rubric}
\rightarrow
\text{Judge}
\rightarrow
\text{Bias Control}
\rightarrow
\text{Human Calibration}
\rightarrow
\text{Aggregation}
\rightarrow
\text{Statistical Validation}
}
$$

真正高质量的 LLM evaluation，关注的不是：

> **“Judge 给了多少分？”**

而是：

> **“这个 Judge 的判断是否稳定？是否和人类一致？有哪些系统性偏差？最终结论在统计上是否可靠？”**

如果你是在做 **LLM/RAG/Agent 的论文或实际评测系统**，下一步最值得深入的是 **“如何设计一套可复现的 LLM-as-a-Judge Prompt + JSON Schema + Pairwise/Pointwise 实验 + 人工校准 + Bootstrap 显著性检验”**，这会直接落到可以跑实验的层面。
