可以。下面我给你一套**可以直接落地成论文实验 / 内部 Eval Pipeline / Benchmark** 的方案。

我会把它设计成一个完整的闭环：

> **Dataset → Candidate Models → Judge Prompt → Structured JSON → Pointwise/Pairwise → Human Calibration → Bias Test → Bootstrap → Statistical Significance → Final Report**

而且重点放在“**可复现**”三个字上：同样的数据、模型、Prompt、随机种子、聚合方法和统计方法，别人应该能够复现你的结果。

# 一、先定义最终目标

假设你要比较：

在某个任务上的表现。

# 三、第一步：先固定 Evaluation Dataset

这是最容易被忽略、但实际上最重要的部分。

## 3.1 Dataset 不要只有 query

建议每条样本至少包含：

```json
{
  "sample_id": "qa_000001",
  "task": "rag_qa",
  "query": "什么是Transformer？",
  "context": [
    "...",
    "..."
  ],
  "reference_answer": "...",
  "metadata": {
    "difficulty": "medium",
    "domain": "machine_learning",
    "language": "zh"
  }
}
```

Candidate output 单独存：

```json
{
  "sample_id": "qa_000001",
  "model": "model_a",
  "answer": "..."
}
```

这样：

> Dataset 和 Model Output 解耦。

非常重要。

---

# 四、Dataset 必须分层

不要随机抽 1000 个问题就结束。

建议：

```text
Dataset
├── easy
├── medium
├── hard
├── ambiguous
├── adversarial
├── long_context
├── multi-hop
└── failure_cases
```

比如 1000 条：

| 类型           |  数量 |
| ------------ | --: |
| Easy         | 200 |
| Medium       | 300 |
| Hard         | 250 |
| Ambiguous    | 100 |
| Adversarial  | 100 |
| Long-context |  50 |

这样最终你可以发现：

```text
Model A:
Easy      95%
Medium    88%
Hard      72%

Model B:
Easy      94%
Medium    91%
Hard      83%
```

这比一个：

```text
Overall = 87.3%
```

有价值太多。

---

# 五、第二步：Candidate Output 必须冻结

这是 reproducibility 的关键。

假设：

```text
Model A
Model B
```

不要：

```text
今天跑 Judge
→
明天重新生成 Answer
→
后天再 Judge
```

因为你无法知道差异来自：

```text
Candidate generation
```

还是：

```text
Judge
```

应该：

```text
Dataset
   ↓
Candidate generation
   ↓
Freeze outputs
   ↓
Judge
```

保存：

```json
{
  "sample_id": "001",
  "model": "A",
  "prompt_version": "v3",
  "model_version": "xxx",
  "temperature": 0,
  "answer": "..."
}
```

---

# 六、第三步：设计 Rubric

我建议不要一开始就做：

```text
Overall quality: 1-10
```

而是拆维度。

例如 RAG：

### Dimension 1 — Correctness

> Answer 是否与事实 / reference 一致。

### Dimension 2 — Relevance

> 是否直接回答用户问题。

### Dimension 3 — Completeness

> 是否覆盖问题的重要部分。

### Dimension 4 — Faithfulness

> 是否所有关键 claim 都有 Context 支撑。

### Dimension 5 — Clarity

> 是否清晰、容易理解。

---

# 七、Rubric 要写成“可操作定义”

比如 Correctness：

```text
5:
完全正确，没有实质性错误。

4:
基本正确，仅存在轻微错误或不影响结论的小遗漏。

3:
部分正确，但存在一个或多个重要遗漏。

2:
存在明显事实或推理错误，但仍包含部分有用信息。

1:
核心结论错误、与问题无关或几乎完全错误。
```

这比：

```text
Score correctness from 1 to 5.
```

可靠很多。

---

# 八、一个非常重要的原则：Dimension 尽量正交

不要定义：

```text
Quality
Helpfulness
Goodness
Overall quality
```

这几个东西高度重叠。

更好的：

```text
Correctness
Relevance
Completeness
Faithfulness
Clarity
```

每一个维度都回答不同的问题。

---

# 九、Pointwise Prompt 设计

推荐结构：

```text
SYSTEM

You are an expert evaluator.

Your task is to evaluate a candidate answer according to
the provided evaluation rubric.

You must evaluate the answer itself, not the writing style
alone.

Do not infer information that is not supported by the
provided context.

Follow the scoring definitions exactly.

Return ONLY valid JSON matching the provided schema.
```

然后：

```text
USER

# Task
{task}

# User Query
{query}

# Context
{context}

# Reference Answer
{reference}

# Candidate Answer
{answer}

# Evaluation Rubric

## Correctness
...

## Relevance
...

## Completeness
...

## Faithfulness
...

## Clarity
...

# Evaluation Instructions

For each dimension:

1. Assign an integer score from 1 to 5.
2. Provide a concise evidence-based justification.
3. Do not reward verbosity by itself.
4. Do not penalize an answer merely because its wording differs
   from the reference answer.
5. For faithfulness, only consider information supported by Context.

Return JSON only.
```

---

# 十、JSON Schema

这是整个系统里非常关键的一层。

不要接受：

```text
"我认为这个答案不错，大概 4 分。"
```

这种自由文本。

必须结构化。

例如：

```json
{
  "sample_id": "qa_000001",
  "evaluation": {
    "correctness": {
      "score": 5,
      "reason": "..."
    },
    "relevance": {
      "score": 4,
      "reason": "..."
    },
    "completeness": {
      "score": 4,
      "reason": "..."
    },
    "faithfulness": {
      "score": 5,
      "reason": "..."
    },
    "clarity": {
      "score": 4,
      "reason": "..."
    }
  },
  "overall_score": 4.4
}
```

---

# 十一、建议进一步增加 Evidence

对于 RAG，我特别推荐：

```json
{
  "faithfulness": {
    "score": 4,
    "claims": [
      {
        "claim": "Transformer uses self-attention.",
        "supported": true,
        "evidence": "context_02"
      },
      {
        "claim": "Transformer was introduced in 2017.",
        "supported": true,
        "evidence": "context_01"
      }
    ]
  }
}
```

这样你的 evaluator 就不是：

> “我感觉它挺 faithful。”

而变成：

> “这个答案有 5 个 claims，其中 4 个被 context 支持。”

---

# 十二、Claim-level Faithfulness

可以定义：

$$
F =
\frac{N_{supported}}
{N_{claims}}
$$

例如：

```text
总 claims = 8
supported = 7
```

那么：

$$
F=7/8=0.875
$$

即：

```text
Faithfulness = 87.5%
```

这通常比直接：

```text
Faithfulness = 4/5
```

更加可解释。

---

# 十三、Pointwise Overall Score 怎么算？

不推荐直接让 Judge 自己随便决定。

可以定义：

$$
S =
w_cC+
w_rR+
w_{comp}Comp+
w_fF+
w_{cl}Cl
$$

例如：

$$
S=
0.30C+
0.20R+
0.20Comp+
0.20F+
0.10Cl
$$

这样：

```text
Correctness  = 5
Relevance    = 4
Completeness = 4
Faithfulness = 5
Clarity      = 4
```

得到：

$$
S =
0.3(5)+
0.2(4)+
0.2(4)+
0.2(5)+
0.1(4)
$$

$$
=4.5
$$

注意：

> **权重应该在实验开始之前固定。**

不能看到结果之后才改。

---

# 十四、Pairwise Prompt

Pairwise 的目标不要问：

> “两个答案分别多少分？”

而是：

> **“哪一个更好？”**

Prompt：

```text
SYSTEM

You are an expert evaluator comparing two candidate answers.

Your task is to determine which answer better satisfies the
user's request.

Use the provided rubric.

Do not prefer an answer merely because it is longer,
more verbose, or more stylistically elaborate.

Do not prefer an answer based on its position.

The correct output must be one of:
A
B
TIE

Return valid JSON only.
```

然后：

```text
USER

# Query
{query}

# Context
{context}

# Reference
{reference}

# Answer A
{answer_a}

# Answer B
{answer_b}

# Criteria

1. Correctness
2. Relevance
3. Completeness
4. Faithfulness
5. Clarity

Which answer is better?

Return:
- winner
- reason
- confidence
```

---

# 十五、Pairwise JSON Schema

推荐：

```json
{
  "sample_id": "qa_000001",
  "winner": "B",
  "tie": false,
  "reason": "B is more complete and better grounded in the provided context.",
  "confidence": 0.86
}
```

如果允许 Tie：

```json
{
  "winner": "TIE",
  "tie": true,
  "reason": "Both answers are essentially equivalent in correctness and completeness.",
  "confidence": 0.71
}
```

---

# 十六、Pairwise 最重要的实验：Position Swap

这是必须做的。

第一次：

```text
A
B
```

第二次：

```text
B
A
```

例如：

```text
Trial 1:
A vs B → A

Trial 2:
B vs A → A
```

注意第二次输出的：

```text
A
```

实际上是：

> 第二个位置的答案。

所以需要还原成 candidate identity。

最终：

```text
Trial 1 → Candidate A
Trial 2 → Candidate A
```

说明一致。

---

# 十七、定义 Position Consistency

设：

$$
y_1
$$

是 A first 的结果，

$$
y_2
$$

是 B first 的结果。

定义：

$$
PC =
\frac{\# consistent\ pairs}
{\# total\ pairs}
$$

例如：

```text
1000 samples

Consistent = 913

PC = 91.3%
```

如果只有：

```text
60%
```

说明 Judge 的 position bias 非常严重。

---

# 十八、最好不要只做一次 Judge

即使：

```text
temperature = 0
```

也不能自动假设：

> 完全 deterministic。

因为 API/model/backend/version 等仍可能导致差异。

推荐：

```text
K = 3
```

例如：

```text
sample_001

Judge 1 → A
Judge 2 → A
Judge 3 → B

Final → A
```

用 majority vote。

---

# 十九、Pairwise 的聚合

例如：

```text
A wins = 580
B wins = 370
Tie     = 50
```

如果把 Tie 排除：

$$
WinRate(A)=
\frac{580}{580+370}
$$

$$
=61.05\%
$$

但你必须明确：

> Tie 怎么处理。

---

# 二十、Tie 有三种常见处理方式

### 方法 A：排除 Tie

$$
WR_A =
\frac{A}
{A+B}
$$

优点：

简单。

缺点：

丢信息。

---

### 方法 B：Tie = 0.5

$$
WR_A=
\frac{A+0.5T}
{A+B+T}
$$

例如：

```text
A = 580
B = 370
Tie = 50
```

那么：

$$
WR_A=
\frac{580+25}{1000}
=60.5\%
$$

---

### 方法 C：单独报告

我最推荐论文里：

```text
A win = 58.0%
B win = 37.0%
Tie    = 5.0%
```

同时再给：

```text
Tie-adjusted win rate = 60.5%
```

透明度最高。

---

# 二十一、Human Calibration：这是整个系统的“地基”

现在进入最重要的部分。

你不能直接说：

> GPT Judge 认为 A 好，所以 A 好。

必须先验证：

> **GPT Judge 和人类专家是否一致？**

---

# 二十二、Human Calibration Dataset 怎么抽？

不要随机抽完事。

推荐：

```text
500 samples
```

其中：

```text
100 easy
150 medium
150 hard
50 ambiguous
50 adversarial
```

如果预算允许：

```text
1000+
```

更好。

---

# 二十三、人类标注最好 Blind

Human evaluator 不应该知道：

```text
这是 GPT-5
这是 Claude
这是我们的模型
```

应该匿名：

```text
Answer A
Answer B
```

否则会产生：

> brand/model bias。

---

# 二十四、Human Annotation Protocol

给人类 evaluator：

```text
Query
Context
Reference
Answer A
Answer B
Rubric
```

然后：

```text
Which is better?

A
B
Tie
```

同时最好让一部分数据被：

```text
Human 1
Human 2
Human 3
```

重复标注。

---

# 二十五、为什么需要多个 Human？

因为：

> Human 也不是 ground truth oracle。

例如：

```text
Human 1 → A
Human 2 → A
Human 3 → B
```

说明这个 case 本身可能 ambiguous。

所以先计算：

> **Human-Human Agreement**

再计算：

> **LLM-Human Agreement**

这是非常关键的。

---

# 二十六、Human-Human Agreement

例如：

```text
Human 1 vs Human 2 = 88%
Human 1 vs Human 3 = 84%
Human 2 vs Human 3 = 86%
```

说明：

```text
Human agreement ≈ 86%
```

如果：

```text
Human agreement = 65%
```

那么你让 Judge 达到 95% agreement 几乎没有意义。

因为：

> 任务本身就存在很高 ambiguity。

---

# 二十七、LLM Judge 应该达到什么水平？

不是简单：

> Accuracy > 80% 就行。

更合理：

$$
Agreement(Judge,Human)
$$

至少接近：

$$
Agreement(Human,Human)
$$

例如：

```text
Human-Human = 86%

Judge-Human = 84%
```

这是非常不错的结果。

如果：

```text
Human-Human = 86%
Judge-Human = 62%
```

那这个 Judge 不适合。

---

# 二十八、Cohen's Kappa

对于两个 evaluator：

```text
Human
Judge
```

可以计算：

$$
\kappa =
\frac{p_o-p_e}{1-p_e}
$$

其中：

```text
po = observed agreement
pe = expected agreement by chance
```

一般报告：

```text
Accuracy = 84.2%
Cohen's κ = 0.71
```

不要只报告 accuracy。

---

# 二十九、如果是多个人类：Fleiss' Kappa

如果：

```text
Human 1
Human 2
Human 3
Human 4
```

都对同一批数据标注：

可以使用：

> Fleiss' κ

或者其他 multi-rater agreement metric。

---

# 三十、如果是 ranking：Kendall / Spearman

例如 Human ranking：

```text
A > C > B > D
```

Judge：

```text
A > B > C > D
```

可以：

$$
Spearman\ \rho
$$

或者：

$$
Kendall\ \tau
$$

通常 Kendall 对 ranking disagreement 更直观。

---

# 三十一、Calibration 不仅是“比较一致率”

更好的 calibration pipeline：

```text
Human Annotation
       ↓
Human-Human Agreement
       ↓
Judge Annotation
       ↓
Judge-Human Agreement
       ↓
Bias Analysis
       ↓
Prompt Revision
       ↓
Repeat
```

这是一个：

> **iterative evaluator development process**

但注意：

> Calibration set 和最终 test set 必须分开。

否则会产生 evaluator overfitting。

---

# 三十二、Train / Calibration / Test 三分法

如果你非常认真地做 benchmark，我推荐：

```text
Dataset
├── Judge Development Set
├── Human Calibration Set
└── Final Test Set
```

例如：

```text
1000 samples

200 → Prompt development
300 → Human calibration
500 → Final evaluation
```

Prompt 修改只能使用前 500 条的信息。

最后 500 条：

> **锁死。**

不能再看结果后修改 Prompt。

---

# 三十三、这是 Reproducibility 最关键的一条

最终 Test Set 必须：

> **盲测。**

即：

```text
Prompt v3
Judge model X
Temperature 0
Test set
```

跑完。

如果结果不好：

```text
“我们改一下 prompt 再跑”
```

然后从结果里选最好的。

这是：

> evaluator overfitting。

---

# 三十四、Bias Test：至少做这 6 项

成熟的 LLM Judge evaluation，我建议至少测试：

```text
1. Position bias
2. Verbosity bias
3. Self-preference
4. Formatting bias
5. Reference bias
6. Language bias
```

---

# 三十五、Position Bias

实验：

```text
A-B
B-A
```

看：

$$
P(A|A\ first)
$$

和：

$$
P(A|B\ first)
$$

差多少。

例如：

```text
P(A | A first) = 62%
P(A | B first) = 51%
```

那么：

```text
Position bias = 11 percentage points
```

这是很明显的 bias。

---

# 三十六、Verbosity Bias

构造：

```text
Answer A = short, correct
Answer B = long, correct
```

语义质量基本一样。

如果：

```text
B win rate = 75%
```

那么：

> Judge 明显偏好长答案。

可以做 paired controlled experiment。

---

# 三十七、Self-preference Bias

例如三个 candidate：

```text
Judge = Model X

Candidate:
X
Y
Z
```

比较：

```text
P(X wins)
P(Y wins)
P(Z wins)
```

控制答案质量后，如果：

```text
X > Y
X > Z
```

显著高于预期：

> 怀疑 self-preference。

---

# 三十八、Formatting Bias

同一个答案：

```text
Version A:
普通 prose

Version B:
Markdown headings + bullets
```

语义完全一样。

如果：

```text
B consistently wins
```

说明 Judge 可能把 formatting 当成 quality。

---

# 三十九、Language Bias

例如同一个答案：

```text
Chinese
English
Japanese
```

语义等价。

测试：

```text
P(win | language)
```

如果明显不同：

> Judge 可能存在 language preference。

---

# 四十、Bootstrap：为什么一定推荐？

假设：

```text
A win rate = 58%
```

你真正想知道的是：

> 这个 58% 稳不稳定？

而不是：

> 样本里恰好是 58%。

Bootstrap 是一个非常实用的方法。

---

# 四十一、Bootstrap 的基本思想

假设有：

```text
N = 1000 samples
```

你从原数据：

```text
sample 1
sample 2
...
sample 1000
```

有放回抽样：

```text
1000 samples
```

得到：

```text
Bootstrap dataset 1
```

重复：

```text
10,000 times
```

每次计算：

$$
WinRate_A
$$

最终得到：

```text
10000 win rates
```

形成 empirical distribution。

---

# 四十二、Bootstrap 代码逻辑

伪代码：

```python
scores = [
    1, 1, 0, 1, 0, ...
]

bootstrap_scores = []

for i in range(10000):
    sample = np.random.choice(
        scores,
        size=len(scores),
        replace=True
    )

    bootstrap_scores.append(
        np.mean(sample)
    )
```

然后：

```python
lower = np.percentile(
    bootstrap_scores,
    2.5
)

upper = np.percentile(
    bootstrap_scores,
    97.5
)
```

得到：

```text
Win Rate = 58.0%
95% CI = [54.9%, 61.1%]
```

---

# 四十三、Pairwise Bootstrap 更应该“按样本”重采样

这是一个非常重要的细节。

如果：

```text
每个 query 都有一个 A vs B 判断
```

那么 bootstrap unit 应该是：

> **query/sample**

而不是：

> token / sentence / judge output。

即：

```text
sample_001
sample_002
sample_003
...
```

整个 sample 一起被抽取。

---

# 四十四、如果每个样本有多个 Judge？

例如：

```text
sample_001

Judge 1 → A
Judge 2 → A
Judge 3 → B
```

不要把这三个结果当成三个独立样本。

因为它们共享：

```text
same query
same candidates
```

存在 cluster dependence。

更好的：

> **cluster bootstrap by sample**

也就是：

```text
Bootstrap sample_001 as a whole
Bootstrap sample_002 as a whole
...
```

---

# 四十五、Bootstrap 显著性检验

假设：

```text
A win rate = 58%
B win rate = 42%
```

你想知道：

$$
H_0:
P(A>B)=0.5
$$

是否可以拒绝？

可以使用：

### Permutation test

非常适合 pairwise comparison。

---

# 四十六、Permutation Test

原始结果：

```text
A wins = 580
B wins = 420
```

观察到：

$$
\Delta = 0.58-0.50=0.08
$$

然后在 null hypothesis：

> A 和 B 本质没有差异。

下随机交换每个 pair 的标签：

```text
A/B → B/A
```

重复：

```text
10,000 times
```

得到 null distribution。

计算：

$$
p =
P(|\Delta_{null}|
\ge
|\Delta_{observed}|)
$$

如果：

```text
p < 0.05
```

则认为：

> A 的优势具有统计显著性。

---

# 四十七、为什么我更推荐 Pairwise + Bootstrap + Permutation？

因为三者作用不同：

### Pairwise

解决：

> Judge 更容易做相对判断。

### Bootstrap

解决：

> 不确定性 / confidence interval。

### Permutation test

解决：

> A 是否显著优于 B。

组合起来：

```text
Pairwise preference
        ↓
Win Rate
        ↓
Bootstrap CI
        ↓
Permutation p-value
```

非常完整。

---

# 四十八、一个完整的最终报告应该长这样

例如：

```text
Model A vs Model B

A wins: 58.2%
B wins: 37.4%
Tie:     4.4%

Tie-adjusted A win rate:
60.4%

95% Bootstrap CI:
[57.1%, 63.7%]

Permutation test:
p = 0.003

Model A significantly outperforms Model B.
```

但还要同时给：

```text

84.7%

Human-Human Agreement:
87.1%

Position Consistency:
93.2%
```

这样结论就非常完整。

# 四十九、Pointwise 和 Pairwise 不应该二选一

我推荐：

```text
              Evaluation
                   │
         ┌─────────┴─────────┐
         ↓                   ↓
     Pointwise             Pairwise
         │                   │
         ↓                   ↓
  Quality dimensions     Model comparison
         │                   │
         ↓                   ↓
  Error analysis         Win rate
```

### Pointwise 回答：

> “这个答案哪里不好？”

### Pairwise 回答：

> “A 和 B 哪个更好？”

这两个问题完全不同。

# 五十六、一个关键改进：不要让 Judge 自己算 Overall

比如：

```text
Correctness = 5
Relevance = 4
Completeness = 4
Faithfulness = 5
Clarity = 4
```

不要让 LLM 输出：

```text
Overall = 4.6
```

而应该由程序计算：

$$
S =
0.3C+
0.2R+
0.2Comp+
0.2F+
0.1Cl
$$

这样：

> **aggregation 是 deterministic 的。**

避免 Judge 出现：

```text
5 + 4 + 4 + 5 + 4
→
4.7?
```

这种不可控行为。

# 五十七、甚至 Score 也可以不要直接平均

如果你的业务是：

> 正确性绝不能低于 3。

那么简单 weighted average 就有问题。

例如：

```text
Correctness = 2
Style = 5
Relevance = 5
```

平均：

$$
4.0
$$

看起来不错。

但业务上：

> 答错了就是不能接受。

那么可以定义：

$$
Score =
\begin{cases}
0 & Correctness < 3\\
weighted\ score & otherwise
\end{cases}
$$

这种：

> **gating rule**

在 production evaluation 很有价值。

---

# 五十八、推荐使用“硬门槛 + Soft Score”

例如：

```text
Correctness >= 4
Faithfulness >= 4
```

先通过 gate。

然后再比较：

```text
Relevance
Completeness
Clarity
```

结构：

```text
             Candidate
                 ↓
       ┌──────────────────┐
       │ Hard Constraints │
       └────────┬─────────┘
                ↓
             Pass?
           /       \
         No         Yes
         ↓           ↓
       Fail      Soft Score
```

这特别适合：

* RAG
* Customer Support
* Agent
* Safety

# 五十九、如何减少 Judge Prompt 对结果的影响？

做：

> **Prompt sensitivity test**

例如：

```text
Prompt v1
Prompt v2
Prompt v3
```

同样的数据：

```text
v1 → A win 58%
v2 → A win 60%
v3 → A win 57%
```

如果：

```text
57~60%
```

比较稳定。

但如果：

```text
v1 → 70%
v2 → 51%
v3 → 43%
```

说明：

> Evaluation protocol 本身不稳定。

这种情况下不要急着比较模型。

先解决 evaluator。

# 六十、Temperature 应该怎么设置？

如果你的目标是：

> 最大化 reproducibility。

通常推荐：

```text
temperature = 0
```

同时固定：

```text
model version
prompt version
schema
dataset
aggregation
```

但不要把：

> temperature = 0

理解成：

> 结果一定绝对 deterministic。

实际 API/backend 行为仍可能存在差异。

所以：

> **用重复评测实测 stability。**

# 六十一、建议测 Inter-run Reliability

例如：

```text

跑 3 次
```

得到：

```text

Run 2: A wins 57.8%
Run 3: A wins 58.5%
```

很好。

如果：

```text

Run 2: 51%
Run 3: 60%
```

就说明 evaluator 不稳定。

## 最后给你一个“不要踩坑”的版本

如果只记住 8 条，我建议记这 8 条：

1. **先定义 rubric，再选 Judge。**
2. **能 deterministic evaluation 的地方，不要让 LLM 判断。**
3. **模型比较优先使用 pairwise，而不是绝对分数。**
4. **Pairwise 必须做 A/B ↔ B/A position swap。**
5. **Judge 必须经过 human calibration。**
6. **Human-Human agreement 是 Judge-Human agreement 的上限参考。**
7. **最终结果报告 CI，而不是只报平均值 / win rate。**
8. **Test set 一旦锁定，不允许根据测试结果继续修改 Judge Prompt。**

如果把它压缩成一句话，就是：

> **一个可信的 LLM-as-a-Judge 系统，不是“一个 Prompt + 一个 GPT”，而是一个经过 rubric 设计、结构化输出、位置偏差控制、人工校准、可靠性验证和统计推断的 measurement system。**

如果你的目标是**真正实现**，下一步就应该把上面的方法落成一套具体代码：**Python + OpenAI/其他 LLM API + Pydantic JSON Schema + Pointwise/Pairwise Runner + Human annotation CSV + Bootstrap/Permutation test + 最终 Markdown/Excel 报告**。这一步可以直接搭成一个可运行的项目骨架。
