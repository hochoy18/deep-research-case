1SSE 是什么

一句话定义

SSE = 一个保持打开的 HTTP Response，服务器不断按 text/event-stream 格式往里写事件，浏览器持续接收，并且支持自动重连。

它是基于 HTTP 的 服务器 → 客户端单向实时通信机制。核心要点：

  • 底层仍然是 HTTP，不需要协议升级握手（不像 WebSocket）。
  • 请求只有一次，但响应可以持续很久（长连接）。
  • 浏览器原生 EventSource 提供 自动重连 与 断线恢复（Last-Event-ID）。
  • 适合 AI 流式输出、实时日志、任务进度、消息通知、监控数据。

3.2 事件字段格式

每个事件由若干 field: value 行组成，以一个空行结束。

3.3 字段含义速查

字段作用示例
event:事件类型（自定义）event: token
data:事件载荷，可多行拼接data: {"text":"你"}
id:事件 ID，用于断线恢复id: 1745-0
retry:客户端重连等待毫秒retry: 5000
: commentSSE 注释，客户端不触发事件，用于心跳: heartbeat\n\n
⚠ 为什么必须 \n\n ？

空行是 SSE 事件分隔符。少了它客户端会把多条当成同一条；多了它会被截断成空事件。

错误：data: hello \n data: world → 客户端认为是一个事件，data="hello\nworld"。

正确：data: hello \n\n data: world \n\n → 两个事件。

8.2 SSE 端点：GET /api/research/{task_id}/stream

位置：src/agent/app.py:201-225。

@app.get("/api/research/{task_id}/stream")
async def stream_research(task_id: str, request: Request):
    # ① 读取客户端传来的最后事件 ID（断线恢复用）
    last_event_id = request.headers.get("Last-Event-ID", "0")

    async def event_generator():
        try:
            async for event_str in read_task_events(task_id, last_event_id):
                # ② 严格按照 SSE 格式：data: ... \n\n
                yield f"data: {event_str}\n\n"
        except Exception as exc:
            yield f'data: {{"error": "{exc}"}}\n\n'

    # ③ 设置必备 Header + 禁用 Nginx 缓冲
    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # ← 关键
        },
    )

8.7 前端消费：useResearchStream.ts

// frontend/src/lib/useResearchStream.ts
const es = new EventSource(`${API_BASE_URL}${stream_url}`);

es.onmessage = (e) => {
    const raw = JSON.parse(e.data);

    // ── 处理 token 流式事件 ──
    if (raw.token) {
        const { text, node } = raw.token;
        if (node !== streamingNodeRef.current) {
            streamingNodeRef.current = node;
            setStreamingNode(node);
            setStreamingContent(text);
        } else {
            streamingContentRef.current += text;
            setStreamingContent(prev => prev + text);
        }
        return;
    }

    // ── 处理终止事件 ──
    if (event.finalize_answer) { es.close(); }
    if (event.task_paused)    { es.close(); }
    if (event.error)          { es.close(); }
};

前端用 useRef + setState 双缓冲：ref 避免闭包过期，state 触发 UI 重渲染。节点切换时自动清空旧节点的流式 buffer。

9Redis Stream 解耦原理

Worker 协程写入 Redis · SSE HTTP 协程从 Redis 读出

为什么选 Redis Stream 而不是 Pub/Sub？

特性Redis Pub/SubRedis Stream（本项目）
消息持久化❌ fire-and-forget✅ 持久化到内存
断线即丢是否，可重读
Last-Event-ID 支持❌ 无法定位✅ 按 msg_id 精确定位
消费者组❌✅ XREADGROUP
容量限制无MAXLEN 500 / EXPIRE 24h
base_knowledge 第 24 节提到的是 Pub/Sub

但 Pub/Sub 断线即丢，无法满足 SSE 的断线重连。本项目用 Stream 是更稳妥的工程选择。

10断线重连 · Last-Event-ID 机制

Last-Event-ID 机制：浏览器记录最后 ID，重连时带上，服务端从该 ID 之后续推

项目实现：read_task_events（task_queue.py:315-351）

async def read_task_events(task_id: str, last_event_id: str = "0"):
    # Redis Stream 的 msg_id 作为 SSE 事件游标
    current_id = last_event_id

    while True:
        result = await r.xread(
            {stream_key: current_id},     # ← 从 last_event_id 之后读
            block=5000,                  # 阻塞 5s
            count=10,
        )
        if result:
            for _, messages in result:
                for msg_id, data in messages:
                    event_str = data.get("event", "{}")
                    current_id = msg_id  # ← 滚动游标
                    yield event_str

                    # 终止事件 → 关闭 SSE
                    event = json.loads(event_str)
                    if any(k in event for k in ("error", "finalize_answer", "task_paused")):
                        return
三个细节

1. current_id = msg_id 用 Redis Stream 的 msg_id 同时充当 SSE event id，天然对齐。

2. block=5000 阻塞 5 秒，浏览器断开后没有新事件，5s 后 XREAD 超时返回空，自动进入下一轮。

3. 终止事件（finalize_answer / task_paused / error）自动 return 关闭 SSE。

12关键设计亮点 & 与 base_knowledge 的差异

① 提交/拉流分离

# POST 返回 task_id + stream_url
{
  "task_id": "uuid-1234",
  "stream_url": "/api/research/uuid-1234/stream"
}

# 前端再单独 GET 这个 stream_url
const es = new EventSource(stream_url);

好处

  • 提交接口不被流式响应拖死
  • 客户端断开后可重连
  • 同一 task_id 可被多端订阅

② Redis Stream 而非 Pub/Sub

# task_queue.py:107
await r.xadd(TASK_STREAM, {"task": payload}, maxlen=1000)

# task_queue.py:327
result = await r.xread({stream_key: current_id}, block=5000)

# task_queue.py:308
await r.expire(f"research:events:{task_id}", 86400)  # 24h 后过期

为什么

  • Pub/Sub fire-and-forget，断线即丢
  • Stream 持久化 + msg_id，支持 Last-Event-ID 重连
  • maxlen + expire 防止内存爆炸

③ subgraphs=True + 节点名翻译

# task_queue.py:220
async for event in graph.astream(state, config, subgraphs=True):

    "web_search":       "web_research",

意义

  • 穿透子图边界拿内部节点事件
  • 前端不必关心节点来自哪一层
  • __ 开头的事件被过滤（LangGraph 内部）

④ 前端 useRef + setState 双缓冲

// useResearchStream.ts:43-52
const streamingNodeRef = useRef<string | null>(null);
const streamingContentRef = useRef<string>("");

es.onmessage = (e) => {
  if (raw.token) {
    if (node !== streamingNodeRef.current) {
      streamingNodeRef.current = node;          // ref 立刻更新
      setStreamingNode(node);            // state 异步更新
      setStreamingContent(text);
    } else {
      streamingContentRef.current += text;
      setStreamingContent(prev => prev + text);
    }
  }

为什么

  • token 来得太快（毫秒级）
  • 仅靠 setState 可能丢更新
  • ref 保证读最新值，state 触发重渲染
  • 节点切换时自动清空 buffer

⑤ X-Accel-Buffering 显式关闭

# app.py:223
headers={
    "Cache-Control": "no-cache",
    "Connection": "keep-alive",
    "X-Accel-Buffering": "no",  # ← 关键
}

作用

  • Nginx 默认 proxy_buffering on
  • 会把响应攒起来再发 → 流式失效
  • X-Accel-Buffering: no 强制透传

与 base_knowledge 的不同选择（值得注意）

维度base_knowledge 建议本项目做法原因

一句话总结本项目的 SSE 模式

LangGraph 节点的 token 回调通过 Redis Stream 解耦生产与消费，FastAPI 用 StreamingResponse + 原生 text/event-stream 把 Redis Stream 包装成 SSE 流，浏览器 EventSource 边收边渲染 —— 本质上是 "SSE 当作 Redis Stream 的实时出站视图"。
