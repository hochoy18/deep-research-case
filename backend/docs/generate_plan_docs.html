1节点定位

generate_plan 是 LangGraph 工作流的第一个执行节点（从 START 出发直达）。它的职责是：根据用户的初始提问，调用 LLM 生成 一份结构化的研究计划需求单（带 Markdown 进度条），暴露给用户做 Human-in-the-Loop 确认。

flowchart LR S([START]) --> GP[generate_plan] GP -->|evaluate_plan| EP{plan_status?} EP -->|unconfirmed| AWP[awaiting_plan_confirmation] EP -->|confirmed| GQ[generate_query] EP -->|需修改| RP[replan] RP --> GP AWP -.用户确认.-> EP
💡 关键定位：generate_plan 只负责"产出 + 标记 unconfirmed"， 不负责判定是否通过。判定职责在下一个节点 evaluate_plan。

2完整代码

pythondef generate_plan(state: OverallState, config: RunnableConfig) -> OverallState:
    """生成研究计划的LangGraph节点 ..."""
    logger.info("正在生成计划...")
    if state.get("plan_status", "unconfirmed") != "unconfirmed":
        return {}

    configurable = Configuration.from_runnable_config(config)
    agent = Agent(model_id=configurable.query_generator_model)
    agent.set_step_prompt(plan_instructions)
    response = agent.step(
        current_date=get_current_date(),
        research_topic=get_research_topic(
            state.get("messages", []),
            [msg.content for msg in state.get('plan_messages', [])]
        ),
        research_proposal=state.get("plan", "")
    )
    response = Post.extract_pattern(response, pattern="markdown")
    logger.info(state)
    logger.info(response)

    return {
        "messages": [AIMessage(content=response)],
        "plan": response,
        "plan_status": "unconfirmed",
        "plan_messages": [AIMessage(content=response)]
    }

Agent.step 内部细节（来自 base_agent.py）

pythondef step(self, **kwargs):
    step_prompt = self.prompt_format(self.step_prompt, **kwargs)
    for _ in range(3):    # 最多重试 3 次
        try:
            response = self(step_prompt)
            response = self.post_process(response)
            break
        except Exception as e:
            logger.error(traceback.format_exc())
            continue
    return response
  • 字符串替换而非 .format()：避免花括号转义问题
  • 3 次重试容错：单点失败不会让整条研究链路崩
  • post_process 为空操作：普通 Agent 不做 JSON 解析；换成 JsonAgent 时这里会解析 JSON

7提示词设计哲学（Agent 核心）

generate_plan 本质上是一个 Agent 角色扮演节点。 真正决定它行为的是 plan_instructions 这段系统提示。 它的设计哲学可以拆为 四个支柱：

🎭 支柱一 · 角色定位（Role）

提示词第一段就把 LLM 锁定为"专业的科研Agent"：

你的核心使命不是直接回答问题或撰写报告，而是与用户进行结构化对话， 将一个模糊、宽泛的分析需求，通过精准、连续的追问，转化为一个定义清晰、 范围明确、可执行的情报分析任务。

这不是"回答问题"的 Agent，而是"澄清需求"的 Agent —— 这一句就锁死了它的行为模式。

📐 支柱二 · 过程协议（Process Protocol）

五步"澄清循环"是 Agent 行为的剧本，每一步都有明确动作：

  • 解构 → 把语言映射到五要素模板
  • 评估 → 量化模糊度
  • 建议 → 主动给默认项
  • 可视化 → 进度条推动对话
  • 锁定 → 明确终止条件

每一步都带示例（"正确示范"、"示例1-4"），让 LLM 知道长什么样算合格。

🎯 支柱三 · 主动智能（Proactive Intelligence）

这是与一般"问答模板"最大的区别 —— Agent 会被要求主动给方案：

当"认知作战"概念模糊时，你可以主动将其拆解："关于民进党策略， 是否需要我深化分析其'舆论斗争'手段（如贴标签、威胁）和'认知作战'路径 （如利用外媒、智库合作）？"

提示词中"动态信源调整建议"那段更进一步：要求 Agent 主动判断并动态扩充信源，触发条件、信源类型、用户确认话术都写得清清楚楚。

🚦 支柱四 · 终止条件（Stop Condition）

Agent 必须有一个明确的"何时结束"的信号，否则会陷入无限追问：

以上需求若无遗漏，请回复【需求确认】。 若需补充或调整，请直接说明。 在得到您的确认后，我将开始生成报告。

这句话同时承担三个作用：① 给出关键词 需求确认 让后端 evaluate_plan 路由判定；② 给用户明确预期；③ 防止 Agent 在最后一轮过度发挥。

为什么 prompt 是"Agent 系统"的关键资产？

代码侧职责提示词侧职责协作结果
get_research_topic 拼接上下文 五要素模板让 LLM 知道读什么 上下文被充分利用，不会浪费 token
extract_pattern 抽取 markdown 强制 markdown fence 输出格式 正则能稳定命中，节点不会崩溃
plan_status 路由 "回复【需求确认】"终止话术 用户行为 → 状态机迁移 → 进入研究阶段
plan_messages 子流 五步澄清循环 + 进度条 多轮交互不污染主对话历史
✅ 一句话总结：generate_plan 的 Python 代码只是"骨架"， 让 LLM 真正按剧本演戏的是 plan_instructions。 修改这个提示词就是在"训练"这个 Agent 角色，而不需要改一行代码。

python# post.py
@staticmethod
def extract_pattern(text, pattern):
    text = Post.strip_think_tags(text)    # 先剥思考块
    pattern = re.compile(rf"\`\`\`{pattern}\s(.*?)\`\`\`", re.DOTALL)
    matches = pattern.findall(text)
    return matches[0] if matches else text
✅ 容错要点：剥 think 在前、匹配 markdown fence 在后， 避免思考块污染 fence 边界；未命中 fence 时原样返回，保证节点不会因为 LLM 输出格式异常而崩溃。

触发迁移的关键代码（evaluate_plan 节选）

pythondef evaluate_plan(state, config):
    plan = state.get("plan", None)
    if state.get("plan_status", "unconfirmed") == "unconfirmed":
        return "awaiting_plan_confirmation"
    if not plan:
        return "replan"
    context = get_last_user_response(state["messages"])
    if "开始研究" in context or "需求确认" in context:
        return GENERATE_SEARCH_NODE
    result = JsonAgent(keys=PlanReflection).step(plan=plan, context=context)
    return GENERATE_SEARCH_NODE if result.satisfy else "replan"

它只是把 plan_status 重置为 unconfirmed，不调用 LLM； 真正"重新生成"由下一次进入 generate_plan 完成。

12设计亮点

① plan_status 早退

避免确认后重复生成，节点具备幂等性。

② 独立 plan_messages 子流

防止计划确认对话污染研究对话主历史。

③ 普通 Agent 而非 JsonAgent

计划是长 Markdown，不是结构化字段，强行 JSON 反而会损失表达力。

④ Post 容错提取

先剥 think、再匹配 fence，未命中原样返回，不让节点崩溃。

⑤ research_proposal 复用上版

replan 时实现"基于上一版迭代"，避免从零开始。

⑥ Agent Prompt 即剧本

plan_instructions 把 LLM 训练成"科研澄清 Agent"，代码只负责调度。

一句话总结

generate_plan 是一个人机协同的"需求澄清节点"： 代码提供骨架，提示词提供剧本。LLM 按剧本与用户多轮澄清需求， 输出停在 unconfirmed 状态等待用户确认；用户确认后由 evaluate_plan 放行进入正式研究流程；若用户要求修改，则基于上一版计划重新生成。
