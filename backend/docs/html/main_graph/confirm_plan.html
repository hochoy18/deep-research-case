一、节点总览

confirm_plan 定义于 src/agent/graph.py:111-141， 是 Deep Research 主图（MainGraph）中"计划阶段"的第二个核心节点， 紧跟在 generate_plan 之后，由 evaluate_plan 路由函数选中进入。

核心职责

职责说明
1️⃣ 意图识别 判断用户对当前计划的回复是「确认」还是「要求修改」
2️⃣ 时效性定级 设置 fresh_level（high/medium/low）供下游研究子图过滤过期材料
3️⃣ 路径分叉 决定下一步：进入研究阶段 / 触发重新规划
4️⃣ 兜底保护 LLM 调用失败时默认进入研究，避免流程卡死
节点本质：confirm_plan 是一个带状态机的智能路由器—— 它不仅执行 LLM 调用，还要根据调用结果决定整个流程的去向。

一句话总结

用户回复 → 关键词短路 OR LLM 意图识别 → 决定「继续研究」或「重新规划」，并把时效性需求固化为 fresh_level。

三、函数签名与参数

完整源码

async def confirm_plan(state: OverallState, config: RunnableConfig) -> dict:
    """评估计划确认并设置新鲜度等级。

    仅当 plan_status 为 "confirmed"（用户已提交确认）时进入此节点。
    根据用户消息中的关键词或 LLM 评估结果，决定是进入研究阶段还是重新规划。
    """
    configurable = Configuration.from_runnable_config(config)
    context = get_last_user_response(state["messages"])

    if "开始研究" in context or "需求确认" in context:
        logger.info("[MainGraph] plan explicitly confirmed → research")
        return {"fresh_level": "medium"}

    agent = JsonAgent(model_id=configurable.query_generator_model, keys=PlanReflection)
    agent.set_step_prompt(plan_reflection_instructions)
    result = await agent.astep(
        research_proposal=state.get("plan", ""),
        context=context,
    )
    if not isinstance(result, PlanReflection):
        logger.warning(
            f"[MainGraph] 计划评估模型调用失败（返回类型={type(result).__name__}），"
            f"默认进入研究阶段"
        )
        return {"fresh_level": "medium"}
    if result.satisfy:
        logger.info("[MainGraph] plan implicitly confirmed → research")
        return {"fresh_level": getattr(result, "fresh_level", "medium")}

    logger.info("[MainGraph] 计划未确认 → 重新计划")
    return {"plan_status": "unconfirmed"}

参数与返回值

类型名称说明
输入 state: OverallState LangGraph 全局状态（含 plan / messages / plan_status）
输入 config: RunnableConfig LangGraph 运行配置（含 configurable.query_generator_model）
输出 {"fresh_level": str} 进入研究阶段时设置时效性等级
输出 {"plan_status": "unconfirmed"} 用户不满意时重置状态，触发重新规划

六、关键词短路逻辑

源代码

if "开始研究" in context or "需求确认" in context:
    logger.info("[MainGraph] plan explicitly confirmed → research")
    return {"fresh_level": "medium"}

设计意图

维度说明
目的 对明确表达确认的用户意图跳过昂贵的 LLM 调用，节省成本
关键词 1 「开始研究」—— 用户用行动词表达推进意愿
关键词 2 「需求确认」—— 与 plan_instructions 第五步的「需求确认」话术闭环呼应
匹配方式 Python in 子串匹配（不区分大小写、不分词）
副作用 fresh_level 被硬编码为 "medium"，不读取 LLM 评估
潜在问题：
  • 关键词是中文硬编码，不利于多语言扩展
  • "开始研究" 出现在任何用户消息中都会触发，包括用户在评论中提到这四个字
  • fresh_level 永远写死为 medium，即使研究主题是"今天比特币价格"

八、PlanReflection Schema

这是 JsonAgent 强约束的输出契约。

定义（src/agent/tools_and_schemas.py:26-33）

class PlanReflection(BaseModel):
    satisfy: bool = Field(
        description="用户对生成的研究计划是否满意."
    )
    fresh_level: str = Field(
        default="medium",
        description=(
            "时效性需求: 'high' (市场数据/排行/价格), "
            "'medium' (产品/战略/趋势), 'low' (技术原理/历史)"
        )
    )

字段详解

字段类型必填说明
satisfy bool ✓ True = 进入研究；False = 触发 replan
fresh_level str 默认 "medium" 三档时效性，影响下游 KB 检索的 max_age_days

九、fresh_level 三档时效

fresh_level 是个看似不起眼、实际影响下游 KB 检索策略的关键参数。

三档时效定义

等级适用场景示例
high 市场数据 / 排行榜 / 价格 今天 BTC 价格、A 股龙头股排行
medium 产品 / 战略 / 趋势 竞品最新动态、行业趋势
low 技术原理 / 历史 / 经典理论 TCP 协议原理、相对论

对下游研究子图的影响

fresh_level 被写入 OverallState，由 research_agent.py 读取：

十一、下游路由 route_after_confirm

confirm_plan 之后由 route_after_confirm（graph.py:144-148）决定下游。

路由逻辑

def route_after_confirm(state: OverallState) -> str:
    """计划确认后的路由：进入研究阶段或重新规划。"""
    if state.get("plan_status", "confirmed") == "unconfirmed":
        return "replan"
    return RESEARCH_AGENT_NODE

路由决策表

confirm_plan 输出state.plan_status下游节点
{"fresh_level": "medium"}（显式） confirmed（未改动） research
{"fresh_level": "high/low"}（隐式） confirmed（未改动） research
{"plan_status": "unconfirmed"} unconfirmed（已重置） replan

为什么用「状态重置」而不是「直接路径」

解耦设计：confirm_plan 只输出状态增量（plan_status 的值）， 把"去 replan 还是去 research"的判断交给下游 route_after_confirm。 这避免了 confirm_plan 既要决策又要路由的双重职责，符合 LangGraph「节点决策、路由函数分发」的最佳实践。

十二、核心设计要点

设计哲学

  • 双层判定（关键词 + LLM）：先尝试快速路径，省 LLM 成本；失败/歧义时再调 LLM
  • 三路径乐观偏向：显式 / 兜底 / 隐式确认都默认推进，只在 LLM 明确否定时才回退
  • 结构化输出契约：用 Pydantic PlanReflection 约束 LLM 输出，避免脏 JSON
  • 类型校验 + getattr 兜底：即使 LLM 漏字段也不会崩溃
  • 状态重置而非直跳：保持 LangGraph 节点「只改状态，不直接跳路由」的契约

十三、潜在改进点

1. 关键词硬编码丢失 fresh_level 信息

显式路径强制 fresh_level="medium"，即使用户说"开始研究今天比特币"也会被降级。 建议改为：关键词匹配后仍然调 LLM 仅评估 fresh_level，或允许用户消息中显式标注时效（"!fresh=high"）。

2. 关键词是中文硬编码、不分词

"开始研究" 在用户消息中任何位置出现都会触发，包括：

  • 评论中提到"我希望系统能开始研究"
  • 引用他人话语：「他说'开始研究吧'但其实我不满意」
建议改用全消息严格匹配或 LLM 语义判断。

3. LLM 失败兜底可能掩盖问题

当 isinstance(result, PlanReflection) 为 False 时直接进入研究， 没有告警/重试。连续失败可能导致用户的不满意反馈被静默忽略。 建议：失败时 增加 retry，或 回退到 awaiting_plan_confirmation 让用户再确认一次。

4. satisfy=False 时丢失 fresh_level

当 LLM 返回 satisfy=False 时，只回写 plan_status=unconfirmed， 不保存 LLM 评估出的 fresh_level。 下一轮澄清-重新规划后，fresh_level 会被默认 medium 覆盖， 丢失上下文。建议：即使回退也保留 LLM 评估结果作为下次参考。

5. 没有超时控制

agent.astep(...) 没有 timeout 配置，如果 LLM 服务挂起，整个 confirm_plan 会卡住， 进而阻塞整张图。建议传入 timeout 参数。

6. 不支持多轮「不满意」的状态累积

每次 satisfy=False 都触发一次 replan，但没有「replan 次数上限」， 用户持续拒绝可能陷入死循环。建议加 max_replan_count 状态字段，达到上限后强制进入研究或结束。
