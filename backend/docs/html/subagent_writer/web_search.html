一、节点总览

_web_search 定义于 src/agent/sub_agents/research_agent.py:178-261， 是 ResearchAgent 子图的核心执行单元。 每次 LangGraph 的 Send 扇出都会触发一个本节点实例，处理单条查询的端到端搜索 + 摘要 + 入库。

核心职责

职责说明
1️⃣ 搜索 通过 MCP（Model Context Protocol）调用外部搜索引擎，拿到 N 条候选结果
2️⃣ 精排 用交叉编码器（cross-encoder）rerank 候选结果，过滤低相关度条目
3️⃣ URL 短化 把长 URL 映射为短 URL（https://search.com/id/{id}-{idx}），便于下游引用
4️⃣ 摘要 用 LLM 把多个搜索结果合并成带源引用的精炼文本
5️⃣ 入库 从摘要中抽取结构化事实，存入 Milvus KB（用于后续任务复用 + 时效性过滤）
节点本质：_web_search 是一个五合一复合节点—— 它把搜索、精排、引用、摘要、入库 5 个动作聚合在一个异步函数内， 避免在图结构中串 5 个节点带来的额外 state 传递和路由开销。

一句话总结

一条搜索查询 → MCP 搜索 + Rerank + URL 短化 + LLM 摘要 + KB 入库 → 返回 sources / summary 增量。

完整源码（简化版）

def _web_search(state: WebSearchState, config: RunnableConfig) -> dict:
    configurable = Configuration.from_runnable_config(config)

    # Step 1: MCP 搜索
    searcher = WebSearchAgent()
    response = searcher.step(prompt=state["search_query"], count=10)

    # Step 2: 空结果防御
    if not response:
        return {"sources_gathered": [], "web_search_result": ["未找到..."]}

    # Step 3: 交叉编码器精排
    from agent.reranker import get_reranker
    reranker = get_reranker()
    if reranker.web_enabled and len(response) > 1:
        documents = [f"{i.get('title','')} {i.get('snippet','')}" for i in response]
        reranked = reranker.rerank(query=state["search_query"], documents=documents, ...)
        response = [response[r["index"]] for r in reranked]

    # Step 4: URL 短化
    long2short = resolve_urls(response, state["id"])
    sources = [{"short_url": long2short[item["url"]], "value": item["url"], "label": item["title"]} for item in response]
    raw_results = json.dumps([{"snippet": i["snippet"], "title": i["title"], "url": long2short[i["url"]]} for i in response], ensure_ascii=False, indent=4)

    # Step 5: LLM 摘要
    agent = Agent(model_id=configurable.query_generator_model)
    agent.set_step_prompt(web_searcher_instructions)
    summary = agent.step(query=state["search_query"], current_date=get_current_date(), web_search_result=raw_results)
    summary = Post.extract_pattern(summary, pattern="text")

    # Step 6: KB 入库（异常静默降级）
    try:
        store = _get_kb_store()
        if store:
            extractor = _get_kb_extractor()
            facts = extractor.extract(summary, research_topic=topic)
            # URL 反向还原
            for f in facts:
                f["source_url"] = short2long.get(f["source_url"], f["source_url"])
                f["research_topic"] = topic
            store.add_facts(facts)
    except (...):
        # 静默降级，不影响主流程
        ...

    return {"sources_gathered": sources, "search_query": [state["search_query"]], "web_search_result": [summary]}

设计意图

维度说明
触发条件 response 为 falsy（None / [] / 空字符串）
行为 早退：跳过精排/摘要/入库，直接返回兜底 state
兜底内容 把"未找到结果"作为占位符写入 web_search_result，保证 critique 能拿到非空输入继续评估
对下游影响 critique 会看到"信息不足"，触发新一轮 follow_up_queries 搜索
潜在问题："未找到" 这种占位符会被 critique 视为"已有信息"， 可能误导 LLM 评估。建议改为：空结果时不返回 web_search_result（或返回空 list）， 让 critique 直接判断"无信息"。

输入输出对比

阶段数量含义
MCP 搜索 M ≈ 10 搜索引擎返回的原始候选
交叉编码器 M 对每个 (query, doc) 对打分
Top-K + 阈值过滤 ≤ 5 最终送入 LLM 摘要的精排结果
为什么需要精排：MCP 搜索按"搜索引擎排序"返回结果，未必与查询意图强相关； 交叉编码器能基于语义计算 query-doc 相关度，把弱相关条目筛掉， 显著提升 LLM 摘要质量。

resolve_urls 实现

def resolve_urls(urls_to_resolve: List[Any], id: int) -> Dict[str, str]:
    prefix = "https://search.com/id/"
    resolved_map = {}
    for idx, site in enumerate(urls_to_resolve):
        if isinstance(site, dict) and "url" in site:
            url = site["url"]
            if url not in resolved_map:
                resolved_map[url] = f"{prefix}{id}-{idx}"
    return resolved_map

URL 短化样例

原 URL短 URL
https://www.reuters.com/world/... https://search.com/id/0-0
https://www.bbc.com/news/... https://search.com/id/0-1

设计意图

用途说明
LLM 输入 短 URL 简洁，便于 LLM 在摘要中以 [代号](url) 格式引用
KB 存储 存储短 URL 节省 Milvus 存储空间（事实可能多次写入）
下游渲染 报告输出时通过反向映射 short2long 还原真实 URL
id 隔离 每次 _web_search 实例用 state["id"] 作为短 URL 前缀，避免不同查询的短链接冲突

异常处理分层

设计意图：KB 异常必须不影响主流程

核心原则：KB 是优化层（加速未来检索），不是必要层。 即使 KB 全部失效，搜索结果仍能写入 sources_gathered 和 web_search_result， 主图仍能正常生成报告。这是一种优雅降级设计。

web_search_result List[str] operator.add 多实例并行时累加，critique 用 "---".join() 合并

reducer operator.add 的影响

并行累加语义：当 _fan_out_to_web_search 一次性触发 N 个 _web_search 实例时， 每个实例返回的 sources_gathered 会通过 operator.add 自动合并到主 state。 这意味着同一个 URL 可能被多次写入（不同实例各自短化），需要 critique 去重。

十三、核心设计要点

设计哲学

  • 五合一聚合：搜索 + 精排 + URL 短化 + 摘要 + 入库 集中在单节点内，减少 LangGraph state 传递和路由开销
  • 双重缓存：MCP 搜索层有 get_cached/set_cached；KB 层有 Milvus 向量检索
  • 优雅降级：KB 任何异常都不影响主流程返回（异常被静默吞掉）
  • 异常分层：瞬时错误 warning，永久错误 error，便于运维区分
  • URL 短化双向：输入 LLM 用短 URL 节省 token；KB 入库前反向还原，便于溯源
  • 精排可选：通过环境变量 RERANKER_WEB_ENABLED 控制，不开启时直接走原结果
  • 空结果显式：用"未找到"占位符而非抛异常，让 critique 能继续判断

十四、潜在改进点

1. 空结果兜底可能误导 critique

返回 "未找到关于 X 的搜索结果" 这种占位字符串，会被 critique 当作实际信息评估， 可能错误判断"信息已包含 X"。建议改为：

  • 不写 web_search_result（返回空 list）
  • 或加 web_search_empty: bool 标记，让 critique 显式识别

2. 精排 import 延迟加载

from agent.reranker import get_reranker 在函数内部 import， 看起来是为了避免循环依赖，但每次调用都要重新解析模块， 影响首次调用延迟。建议改为模块顶部 import，或在 _get_kb_store 旁加 _get_reranker 单例。

3. KB 入库同步阻塞

extractor.extract() 和 store.add_facts() 都是同步阻塞调用， 在 N 个并行实例同时执行时会显著拖慢整体耗时。建议：

  • 把 KB 入库改成 asyncio.create_task() 异步后台任务
  • 或用独立线程池执行

4. URL 短链接命名空间冲突风险

resolve_urls 用 state["id"] 作为前缀： https://search.com/id/{id}-{idx}。 但 _route_after_critique 在下一轮用 state["number_of_ran_queries"] + int(idx) 重新计算 id，不同轮次的 id 可能撞车。建议加 query hash 前缀。

5. 多个 KB 抽取实例并发风险

N 个 _web_search 实例并行时，每个都会触发 FactExtractor.extract() （内嵌 LLM 调用）。当 N 较大时（如 5+），可能触发 LLM 速率限制。建议：

  • 对 extract 调用加信号量
  • 或改成批量抽取

6. sources_gathered 可能重复

不同查询可能引用同一个 URL（如多家媒体报道同一事件）， 但 sources_gathered 用 operator.add 累加不做去重， 下游 critique / writer 可能看到重复 URL。建议加 URL 去重逻辑。

7. 没有超时控制

WebSearchAgent.step()、Agent.step()、FactExtractor.extract() 三个 LLM/MCP 调用都没有 timeout，如果某环节卡住，整个 _web_search 实例会无限挂起， 进而阻塞 critique。建议每个调用都加 timeout。

8. rerank 输入可能不够丰富

精排时只用 title + snippet 作为评分文档，没用 url 域名信息。 知名域名（如 reuters.com）可能权威性更高，应纳入评分。
