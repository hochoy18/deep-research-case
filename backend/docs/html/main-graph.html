四、generate_plan（:40-85）

根据用户主题生成研究计划。仅首次任务执行，二次提交时直接跳过。

核心代码

async def generate_plan(state: OverallState, config: RunnableConfig) -> dict:
    if state.get("plan_status", "unconfirmed") != "unconfirmed":
        return {}                                        # ★ 二次提交直接跳过

    configurable = Configuration.from_runnable_config(config)
    agent = Agent(model_id=configurable.query_generator_model)
    agent.set_step_prompt(plan_instructions)

    # 流式调用（emit_token 注入）
    emit_token = config.get("configurable", {}).get("_emit_token")
    if emit_token:
        async def on_token(text: str) -> None:
            await emit_token(text, "generate_plan")
        response = await agent.astream_step(on_token, ...)
    else:
        response = await agent.astep(...)

    response = Post.extract_pattern(response, pattern="markdown")

    return {
        "messages": [AIMessage(content=response)],
        "plan": response,
        "plan_status": "unconfirmed",
        "plan_messages": [AIMessage(content=response)],
    }

五、evaluate_plan（:88-108）— 路由节点

异步路由函数，返回字符串（下一个节点 ID）。

核心代码

async def evaluate_plan(state: OverallState, config: RunnableConfig) -> str:
    if state.get("plan_status", "unconfirmed") == "unconfirmed":
        logger.info("[MainGraph] 等待用户确认计划")
        return "awaiting_plan_confirmation"

    if not state.get("plan"):
        logger.info("[MainGraph] 没有计划可评估 → 重新计划")
        return "replan"

    logger.info("[MainGraph] 计划已提交确认 → 评估")
    return "confirm_plan"

三个返回值的精确含义

返回值触发条件效果对应状态
"awaiting_plan_confirmation" 计划刚生成（plan_status=unconfirmed） 进入暂停节点，等用户确认 首次提交后
"replan" plan_status != unconfirmed 但 plan 为空（异常） 回 generate_plan 重新生成 理论异常态
"confirm_plan" 二次提交（plan_status=confirmed 且 plan 存在） 进入 confirm_plan 评估 用户确认后
异步但无 await：evaluate_plan 是 async def 但内部没有真正的 await 调用，只是为了与 LangGraph 的异步节点签名一致。可以改为 sync 函数（性能影响微乎其微）。

为什么 lambda return state 能暂停？

要素作用
return state节点不修改 state，状态保持不变
无出边LangGraph 推进入度终止
AsyncRedisSaver每次节点完成时自动 checkpoint
相同 thread_id恢复时从该 checkpoint 加载
这是 LangGraph 实现 HITL 的标准模式：透传节点 + 无出边 + checkpointer。 配合 worker 的 task_paused 事件 + 前端 SSE 关闭逻辑 → 完整的暂停-恢复机制。

八、confirm_plan（:111-141）

识别用户消息中的"开始研究"等关键词，或用 LLM 评估计划是否满足需求。

核心代码

async def confirm_plan(state: OverallState, config: RunnableConfig) -> dict:
    configurable = Configuration.from_runnable_config(config)
    context = get_last_user_response(state["messages"])    # 最后一条 human 消息

    # 快速路径：关键词识别
    if "开始研究" in context or "需求确认" in context:
        logger.info("[MainGraph] plan explicitly confirmed → research")
        return {"fresh_level": "medium"}

    # LLM 评估路径
    agent = JsonAgent(model_id=configurable.query_generator_model, keys=PlanReflection)
    agent.set_step_prompt(plan_reflection_instructions)
    result = await agent.astep(
        research_proposal=state.get("plan", ""),
        context=context,
    )

    if not isinstance(result, PlanReflection):
        logger.warning("[MainGraph] 计划评估模型调用失败，默认进入研究阶段")
        return {"fresh_level": "medium"}

    if result.satisfy:
        logger.info("[MainGraph] plan implicitly confirmed → research")
        return {"fresh_level": getattr(result, "fresh_level", "medium")}

    logger.info("[MainGraph] 计划未确认 → 重新计划")
    return {"plan_status": "unconfirmed"}

def route_after_confirm(state: OverallState) -> str:

同步 vs 异步

虽然 evaluate_plan 是 async，但 route_after_confirm 是 sync —— 因为后者不需要任何 await 操作。

LangGraph 路由函数既支持 async 也支持 sync，async 仅在需要 await 时才必要。

十一、图构建与边定义（:150-192）

完整构建代码

def build_graph(checkpointer=None):
    """编译研究智能体图。"""
    builder = StateGraph(OverallState, config_schema=Configuration)

    # 6 个节点
    builder.add_node(GENERATE_PLAN_NODE, generate_plan)
    builder.add_node("confirm_plan", confirm_plan)
    builder.add_node("replan", lambda state, config: {"plan_status": "unconfirmed"})
    builder.add_node("awaiting_plan_confirmation", lambda state, config: state)
    builder.add_node(RESEARCH_AGENT_NODE, research_agent_graph)
    builder.add_node(WRITER_AGENT_NODE, writer_agent_graph)

    # 6 条边
    builder.add_edge(START, GENERATE_PLAN_NODE)                          # 边 1
    builder.add_conditional_edges(                                        # 边 2
        GENERATE_PLAN_NODE,
        evaluate_plan,
        ["confirm_plan", "replan", "awaiting_plan_confirmation"],
    )
    builder.add_conditional_edges(                                        # 边 3
        "confirm_plan",
        route_after_confirm,
        [RESEARCH_AGENT_NODE, "replan"],
    )
    builder.add_edge("replan", GENERATE_PLAN_NODE)                        # 边 4
    builder.add_edge(RESEARCH_AGENT_NODE, WRITER_AGENT_NODE)              # 边 5
    builder.add_edge(WRITER_AGENT_NODE, END)                              # 边 6

    return builder.compile(
        name="pro-research-agent",
        checkpointer=checkpointer,
    )

# langgraph dev 入口
graph = build_graph()

HITL 的三个关键要素

要素代码作用
透传节点 lambda state, config: state 不修改 state，状态保持

十七、设计要点

17.1 路由节点 vs 状态节点

LangGraph 节点分两种语义角色：

类型返回值作用
路由节点str（下一个节点 ID）用于 add_conditional_edges
状态节点dict（state 更新）用于 add_node

17.2 子图嵌入 vs 节点合并

本项目选择子图嵌入而非把所有节点直接合并到父图：

  • 子图独立开发、测试
  • 可被其他父图复用
  • subgraphs=True 让父图能监听子图内部事件

17.3 暂停点设计

核心三要素：

  1. 透传节点：lambda state, config: state
  2. 无出边：让 LangGraph 推进入度终止
  3. Checkpointer：AsyncRedisSaver 自动持久化

17.4 异常防御层级

节点异常处理
generate_plan二次提交跳过；LLM 失败由 astream_step 3 次重试
evaluate_plan仅读 state，无 IO，理论上不会抛异常
confirm_planLLM 失败 → 降级返回 {"fresh_level": "medium"}
replan / awaitinglambda，无异常
子图由各子图自身处理

17.5 潜在改进点

  1. generate_plan 的 emit_token 链路：on_token 闭包中 emit_token 没显式捕获异常 —— 实际上 astream_step 内部有兜底（base_agent.py:256-259），但节点本身没有
  2. evaluate_plan 是 async 但无 await：可改为 sync 函数
  3. confirm_plan 关键词硬编码："开始研究" / "需求确认" 是中文硬编码，国际化困难
  4. replan 节点无 LLM：如果 LLM 在 confirm_plan 中说 plan 不行，只是 reset state，丢失了 LLM 的改进建议
  5. 节点 ID 与函数名不同：builder.add_node("replan", ...) 但函数是 lambda —— 函数追踪困难
  6. plan_messages 字段：仅在 generate_plan 中使用一次（拼接 research_topic），其他节点未使用 —— 可考虑删除
