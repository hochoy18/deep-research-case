一、提示词总览

plan_instructions 定义于 src/agent/prompts.py:9-125， 是 Deep Research 子图入口的需求澄清节点（_clarify）所使用的主提示词。 它的核心目标不是直接回答用户，而是通过结构化对话把模糊需求打磨成可执行的需求单。

核心特征

特征说明
角色定位 科研 Agent 的对话澄清者，非直接答题者
核心方法论 五步「澄清循环」(Clarification Loop)
分析模板 「专报五大关键要素」分析模板
输出形态 Markdown 代码块包裹的需求单（含进度条 + 核心需求 + 待确认问题 + 智能建议）
交互终点 用户回复「需求确认」 → 需求单锁定 → 进入研究执行
设计哲学：这个提示词遵循"先对齐再执行"的原则 —— 在调用任何昂贵资源（KB 检索 / Web 搜索 / LLM 摘要）之前， 先用低成本对话消除需求歧义，从而降低无效检索与重做成本。

二、任务说明与角色定位

原文要点（节选）

# 任务说明
你是一个专业的科研Agent。你的核心使命不是直接回答问题或撰写报告，
而是与用户进行结构化对话，将一个模糊、宽泛的分析需求，
通过精准、连续的追问，转化为一个定义清晰、范围明确、可执行的情报分析任务。

你的最终产出物是一个得到用户确认的、毫无歧义的"最终版任务需求单"。

三个关键定位

维度定位含义
不是 答题者 / 报告撰写者 不直接产出最终报告内容
而是 对话澄清者 / 需求工程师 通过多轮对话把需求打磨清晰
产出 经用户确认的需求单 作为下游研究子图的输入契约
关键边界：即使用户的需求非常清晰，本提示词也不应该跳过澄清直接执行。 它必须走完五步循环（或至少达到 100% 清晰度）后，把"核心需求理解"作为最终产出， 再交给下游 plan_reflection 进行意图识别，最后才进入 ResearchAgent。

四、第一步：解构与模板映射

当 Agent 收到用户的初始需求时，必须立即启用内置的「专报五大关键要素」分析模板， 将用户的模糊语言映射到五个维度上。

关键约束："立即启用"和"必须"两个词表明：模板映射不是可选项， 即使用户的需求看似明确，Agent 也要走一遍模板来确保完整覆盖。

第一步：解构与模板映射 (Deconstruct & Template Mapping)
- 当接收到用户任何一个初始需求时，你必须立即启用内置的
  **"专报五大关键要素"**分析模板，将用户的模糊语言映射到这五个维度上：
  - 核心分析对象 (Subjects)：要分析的是"谁"？（人物、团体、事件）
  - 对手策略维度 (Opponent's Strategy)：是否需要分析对手的应对策略？
  - 风险研判维度 (Risk Assessment)：需要预警哪些潜在风险？
  - 信息时空边界 (Scope & Boundaries)：
    - 时间范围 (Timeframe)
    - 媒体范围 (Media Scope)
    - 具体信源 (Specific Sources)
  - 成果呈现形式 (Output Format)

六、第二步：模糊度评估与问题生成

对五大要素逐一评估用户输入信息的明确度，对模糊要素生成封闭式选择题。

原文要点

第二步：模糊度评估与问题生成 (Ambiguity Assessment & Question Generation)
- 针对上述五个要素，逐一评估用户输入信息的明确度。
- 对于任何模糊不清的要素，你必须主动生成具体的、封闭式的选择题
  或带有建议的引导性问题。

问题生成的 4 个原则

原则说明反例
1️⃣ 封闭式选项 提供 A/B/C 选项，避免开放式问答 ❌ "您想了解哪些媒体？" → ✅ "台湾媒体 / 国际媒体 / 两者都要？"
2️⃣ 具体可执行 选项落到具体的媒体名 / 工具 / 时间窗口 ❌ "请指定信源" → ✅ "联合报 / 自由时报 / TVBS / ETtoday"
3️⃣ 建议引导 提供「默认推荐」+「自定义入口」 ❌ 问完不答 → ✅ "若未指定，我将默认使用...，是否同意？"
4️⃣ 逐个击破 按要素顺序追问，不要一次性把所有问题抛出 ❌ 一次性问 10 个 → ✅ 本轮聚焦 2-3 个核心要素

原文示范（具体信源）

关于「具体信源」，为了确保分析的准确性，您希望我使用Google AI深度搜索哪些台湾媒体 （如：联合报、自由时报）和国际媒体（如：路透社、BBC）的网站？ 请提供一个列表，或者我可以根据常规重要性为您推荐一个。

每次回复都应包含两个部分，让用户直观感受到对话正在推进。

进度条设计意图

进度区间含义Agent 行为
0% ~ 30% 需求非常模糊 抛出 2-3 个最关键的封闭式问题
30% ~ 70% 部分要素已澄清 针对性追问未澄清要素 + 提供默认建议
70% ~ 95% 大部分要素已澄清 启动动态信源调整 + 输出格式确认
95% ~ 100% 全部要素已澄清 进入第五步：锁定与最终确认
可视化是体验核心：进度条让用户持续感知到对话价值， 避免「我到底还要被问多久」的挫败感。

九、第五步：锁定与最终确认

当所有关键要素都已澄清，没有任何「待确认问题」时，整合所有信息形成「核心需求理解 (最终版)」。

标准话术

以上需求若无遗漏，请回复 【需求确认】。
若需补充或调整，请直接说明。
在得到您的确认后，我将开始生成报告。

十二、核心设计要点

设计哲学

  • 先对齐再执行：在调用昂贵资源前，先用低成本对话消除需求歧义
  • 结构化对话：用五步循环约束 Agent 行为，避免"自由发挥"导致跑题
  • 用户确认制：需求单必须经用户回复【需求确认】后才执行，体现"人在回路"
  • 可视化进度：进度条让用户持续感知对话价值，避免挫败感
  • 主动智能：不只追问，还主动提供默认信源 + 分析框架 + 输出格式
  • 动态信源调整：根据任务垂直领域自动扩充信源，区别于通用 RAG

与下游 prompt 的协作

Prompt协作点数据流向
plan_reflection_instructions 判断用户回复是否包含【需求确认】 本 prompt 输出 → 用户回复 → reflection 识别
query_writer_instructions 把澄清后的需求拆解成 N 个搜索查询 最终需求单 → query_writer 拆解
web_searcher_instructions 单条查询的搜索 + 摘要 每个查询 → 搜索 → 摘要
reflection_instructions 判断信息是否充分，决定是否继续搜索 所有 summaries → 反思 → follow_up_queries
