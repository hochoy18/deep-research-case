三、KB 单例管理（:58-82）

延迟初始化 Milvus 客户端 + LLM 抽取器，进程内共享一个连接。

核心代码（简化）

_kb_store: FactStore | None = None          # Milvus 客户端
_kb_extractor: FactExtractor | None = None  # LLM 抽 facts

def _get_kb_store() -> FactStore | None:
    """延迟初始化 + 失败降级为 False sentinel"""
    global _kb_store
    if _kb_store is None:
        try:
            _kb_store = FactStore()                # 连接 Milvus
        except (KBConnectionError, KBConfigError):
            _kb_store = False                       # 失败 → sentinel
    return _kb_store if _kb_store is not False else None

def _get_kb_extractor() -> FactExtractor:
    """延迟初始化 + 无降级"""
    global _kb_extractor
    if _kb_extractor is None:
        _kb_extractor = FactExtractor()
    return _kb_extractor

关键设计

设计说明
延迟初始化 首次调用时才连接 Milvus，避免启动期阻塞
失败降级 FactStore 连接失败 → False sentinel → 后续代码用 if store: 跳过 KB 功能
共享单例 整个进程一个 Milvus 连接，避免重复建立
Extraction 无降级 FactExtractor（仅 LLM 调用）失败时无 sentinel，需要让上层捕获

四、节点 1：_generate_queries（:89-167）

把研究主题分解为 N 个独立的搜索查询，并注入 KB 已有事实。

核心代码（简化）

async def _generate_queries(state, config):
    # 1. 读配置
    configurable = Configuration.from_runnable_config(config)
    if state.get("initial_search_query_count") is None:
        state["initial_search_query_count"] = configurable.number_of_initial_queries

    # 2. KB 检索（避免重复搜索）
    known_facts_text = ""
    store = _get_kb_store()
    if store:
        mode = get_mode()
        topic = get_research_topic(state["messages"])
        freshness = state.get("fresh_level", "medium")
        max_age = FRESHNESS_MAX_AGE.get(freshness, 30)
        hits = store.query(topic, top_k=20, min_confidence=0.6, max_age_days=max_age, ...)
        known_facts_text = format_kb_hits(hits)

    # 3. LLM 生成查询
    agent = JsonAgent(model_id=configurable.query_generator_model, keys=SearchQueryList)
    result = agent.step(
        current_date=...,
        research_topic=topic,
        number_queries=state["initial_search_query_count"],
        research_proposal=state.get("plan", ""),
        known_facts=known_facts_text,
    )

    # 4. 降级处理
    if not isinstance(result, SearchQueryList):
        return {"search_query": [get_research_topic(state["messages"])]}
    return {"search_query": result.query}

五、节点 2：_fan_out_to_web_search（:170-175）

用 LangGraph Send API 把每个查询并行扇出到一个独立的 _web_search 实例。

核心代码（简化）

def _fan_out_to_web_search(state: QueryGenerationState) -> list[Send]:
    return [
        Send(_WEB_SEARCH, {"search_query": q, "id": int(idx)})
        for idx, q in enumerate(state["search_query"])
    ]

LangGraph Send API 说明

  • 不是普通边，是动态并行分发
  • 每个 Send 创建一个独立的 _web_search 副本
  • 所有副本并行执行
  • 副本输出按 operator.add reducer 累积到主 state

七、节点 4：_critique（:264-306）

LLM 评估当前收集的信息是否充分，决定是否继续搜索。

核心代码（简化）

async def _critique(state, config):
    state["research_loop_count"] = state.get("research_loop_count", 0) + 1
    reasoning_model = state.get("reasoning_model") or configurable.reflection_model

    agent = JsonAgent(model_id=reasoning_model, keys=Reflection)
    result = agent.step(
        current_date=...,
        number_queries=state["initial_search_query_count"],
        research_topic=...,
        summaries="\n\n---\n\n".join(state["web_search_result"]),
        research_proposal=state.get("plan", ""),
    )

    if not isinstance(result, Reflection):
        # LLM 失败 → 视为不足，继续搜索
        return {"is_sufficient": False, ...}

    return {
        "is_sufficient": result.is_sufficient,
        "knowledge_gap": result.knowledge_gap,
        "follow_up_queries": result.follow_up_queries,
        "research_loop_count": state["research_loop_count"],
        "number_of_ran_queries": len(state["search_query"]),
        "max_research_loops": state.get("max_research_loops", configurable.max_research_loops),
    }

Reflection schema

class Reflection(TypedDict):
    is_sufficient: bool            # 信息够不够？
    knowledge_gap: str             # 还缺什么？
    follow_up_queries: list[Query] # 下一步该搜什么？

关键字段

字段作用下游使用
research_loop_count循环次数 +1路由判断是否达上限
is_sufficient是否充分路由判断退出
knowledge_gap知识缺口前端展示 / debug
follow_up_queries下一轮查询路由节点扇出新一轮
number_of_ran_queries已执行查询数下一轮 id 续编
降级策略：LLM 返回非 Reflection → 视为"信息不足"，返回默认 follow_up_queries=[]，下一轮无新查询（自然退化为 0 增量）

八、路由：_route_after_critique（:309-323）

决定返回再搜索还是退出子图。是同步函数（不是 async），只返回路由决策。

核心代码（简化）

def _route_after_critique(state, config):
    configurable = Configuration.from_runnable_config(config)
    max_loops = state.get("max_research_loops") or configurable.max_research_loops

    if state["is_sufficient"] or state["research_loop_count"] >= max_loops:
        return END                              # 退出子图 → 父图 writer
    else:
        # 继续搜索：用 follow_up_queries 并行扇出
        return [
            Send(_WEB_SEARCH, {
                "search_query": q,
                "id": state["number_of_ran_queries"] + int(idx)
            })
            for idx, q in enumerate(state["follow_up_queries"])
        ]

关键细节

  • state["number_of_ran_queries"] + int(idx) —— 续编 id，避免与上轮重复
  • 路由返回值可以是 END 或 list[Send]（动态路由）
  • 同步函数：因为只是返回路由决策，不涉及 IO

双重退出保险

条件说明
is_sufficient=True LLM 判断信息已充分
research_loop_count >= max_loops 达到循环上限（防 LLM 永远说"不充分"导致死循环）

13.5 Potential Issues（潜在改进点）

  • KB 抽 facts 是同步阻塞 LLM 调用（_web_search 内）：多个 KB 抽取并行会触发多个 LLM 请求，可能限流
  • 没有超时控制：单个 _web_search 节点可能因 MCP 卡住而长时间挂起
  • _route_after_critique 是同步函数但内部使用 Send：理论上 OK，但若 config 解析失败会抛异常而非返回默认路由
  • KB 错误只 log 不抛出：上游无法感知 KB 不可用，需要通过其他方式监控
