三、参数 1：persistent_graph —— 带 Redis 持久化的可执行图

3.1 初始化代码

checkpointer = AsyncRedisSaver(
    REDIS_URL,
    ttl={"default_ttl": 60 * 24 * 7, "refresh_on_read": True},
)
await checkpointer.asetup()        # 建表（一次性）
_persistent_graph = build_graph(checkpointer=checkpointer)

3.2 能力清单

  • 用 task_id 当 thread_id，所有 channel state 落 Redis，TTL = 7 天
  • 断点续传：用户在 plan 确认时回复"开始研究"再 resume，LangGraph 自动从 Redis 加载上次停在 awaiting_plan_confirmation 那一刻的 state
  • 多任务隔离：每个 task 一个独立 checkpoint，互不污染
注意：asetup() 是异步的（创建 Redis 内部 hash 结构），生产环境通常放进 FastAPI lifespan 钩子，避免每个 worker 第一次任务都阻塞一次。

四、参数 2：initial_state —— 图的"启动输入"

4.1 构造代码

initial_state: dict = {
    "messages": messages,
    "plan_status": task.get("plan_status", "unconfirmed"),
    "plan": task.get("plan", ""),
}

4.2 关键点

  • 只塞了 3 个字段，其余字段（plan_messages、fresh_level、研究结果、最终报告）由节点运行中由 reducer 累积。
  • messages 使用 LangGraph 内置的 add_messages reducer，新消息与历史拼接（按 id 去重）。
  • Resume 场景：用户在 plan 确认后又点"开始研究"，前端在 messages 里追加用户确认消息 + plan_status="confirmed"，初始 state 不再是空 plan，下游 evaluate_plan 走 confirm_plan 分支。
  • 这就是 LangGraph 的"input 是 patch，不是完整 state"思想。
提示：initial_state 的字段会与 checkpointer 中持久化的 state 合并（取 patch 语义），不需要把上次的所有字段都补全。

六、参数 4：subgraphs=True —— 穿透子图边界

这是代码的精髓所在。用 add_node("research", research_agent_graph) 把子图挂进来后，LangGraph 的子图是独立的 Pregel 实例，有自己的 channels 和事件流。

6.1 为什么必须开启？

  • 默认 subgraphs=False：只 yield 顶层节点的事件 —— 前端只能看到 "research" 这个黑盒整体的事件， 看不到里面跑了 generate_queries → web_search → critique。
  • 开 subgraphs=True：事件从子图"穿透"上来，但格式变成带命名空间的二元组。

6.2 行为对比

stream_modesubgraphs事件形态可见节点
"updates" (默认) False {node_name: patch} 仅主图顶层节点
"updates" True (namespace, {node_name: patch}) 主图 + 所有子图内部节点
"values" True (namespace, state_dict) 每步完整 state 快照
["updates", "messages"] True (mode, event) 节点更新 + LLM token 流
注意：若改成 stream_mode="values"，data 会是完整 state 快照，下游 list(data.keys())[0] 就会崩 —— 务必保持 "updates"。

7.3 解析代码

# 跳过非节点事件（边界事件 / 内部生命周期）
if not isinstance(event, tuple) or len(event) != 2:
    continue

namespace: tuple = event[0]
data: dict = event[1]

node_name = list(data.keys())[0]
node_output = data[node_name]

# 跳过 LangGraph 内部节点（__前缀）
if not node_name or str(node_name).startswith("__"):
    continue

10.3 为什么用 finalize_answer 而非透传 write？

writer 子图结束时会通过 add_messages reducer 返回一个包含全部历史的 messages 列表 （含 HumanMessage + 早期 plan AI message）。前端只关心最后一条 AI 输出（即最终报告）， 所以从列表里筛最后一条 ai 类型消息，包装成前端约定的 {"finalize_answer": {"messages": [...]}} 事件再推一遍： 

if frontend_event_name == "write" and isinstance(node_output, dict):
    if "messages" in node_output:
        msgs = node_output["messages"]
        ai_msgs = [m for m in msgs if getattr(m, "type", None) == "ai"]
        final_msg = ai_msgs[-1] if ai_msgs else (msgs[-1] if msgs else None)
        if final_msg:
            final_answer_event = {
                "finalize_answer": {
                    "messages": [{"content": final_msg.content, "type": "ai"}]
                }
            }

十一、易踩的坑

#陷阱规避方法
1 initial_state 是 patch 不是 full state。resume 时只补必要字段，别把 plan 也带上覆盖，否则用户上一次的 plan 草稿会丢。 把 plan 写入走 reducer 而非 state 全量替换。
2 _emit_token 需在每个节点里手动 if-else 读取（graph.py:53），因为 LangGraph 不支持"自定义 token 回调注册"。 未来可以提到 Configuration 里做规范化。
3 子图节点名冲突：主图与子图同名时，光看 node_name 无法区分来源。 必须结合 namespace 联合判断。
4 asetup() 异步：必须在使用前调用。 放进 FastAPI lifespan 钩子，每个进程仅跑一次。
5 TTL 设计：60*24*7=7 天，若 task_paused 后 7 天才确认，会拿不到 checkpoint。 延长 TTL，或在 Redis 流里单独缓存 task 状态。
6 finalize_answer 用 frontend_event_name=="write" 判断，假设主图没有同名节点。 若以后主图有 write 节点，改成 (namespace, node_name) 联合判断。
7 stream_mode 默认 "updates"，data 是 {node: patch} 单 key 字典。 若改 "values"，list(data.keys())[0] 会崩。
8 必须 async for，不能用 for，否则会报 TypeError: 'async_generator' object is not iterable。 在异步上下文消费；同步场景用 .stream()。
