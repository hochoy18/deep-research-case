1概览：这个评估框架做什么

本框架使用 LLM-as-Judge 方法对 DeepResearch Agent 的产出做两类质量评估：

评估层级 1
端到端 (e2e)

对最终研究报告做 5 维度评分（事实 / 覆盖 / 结构 / 时效 / 引用），用于判断整体产出是否可用。

评估层级 2
组件级 (comp)

对每个节点（plan / queries / summarization / critique / citations / plan reflection）独立打分，定位问题节点。

核心机制
LLM-as-Judge

用另一个 LLM 对 agent 产出评分，强制结构化 JSON 输出，Pydantic 强类型校验，1–5 分自动裁剪。

2快速上手（5 分钟跑起来）

Step 1 · 准备环境

# 进入 backend 目录
cd backend

# 首次：安装依赖
pip install -e .

# 确认 .env 配置
cat .env | grep -E "LLM_BASE_URL|APP_TOKEN|MCP_APP_ID"

Step 2 · 快速验证

# 单条 topic 跑端到端（约 1-3 分钟）
python -m eval.run_eval --mode e2e \
  --topic "2025年AI芯片市场趋势"

# 看到 Overall: x.x/5 即成功

Step 3 · 跑完整测试集

# 10 个 topic，端到端 + 组件级
python -m eval.run_eval --mode all \
  --output eval_results.json

Step 4 · 查看报告

# 终端已打印摘要；JSON 在文件中
cat eval_results.json | python -m json.tool | less

# 或只看分数
python -c "import json; \
d=json.load(open('eval_results.json')); \
print(d['timestamp'])"
提示：第一次跑建议先用 --mode e2e --topic "..." 单条验证，避免 10 条全跑等太久。完整跑通常 10–30 分钟（取决于 Judge 模型和搜索响应）。

三种 actual_behavior 判定逻辑

actual_behavior触发条件含义
direct_proceed 用户反馈含硬编码关键字（"需求确认" / "开始研究"） 短路直接继续，不调 LLM 意图识别

4.4 Judge._call：LLM 调用 + 3 次重试

位置：eval/judge.py:167-190。所有评分方法的统一入口。

def _call(self, prompt):
    agent = Agent(model_id=self.model_id)
    for attempt in range(3):
        try:
            raw = agent(prompt)
            json_str = Post.extract_pattern(raw, pattern="json")
            return json.loads(json_str)
        except Exception:
            continue  # 失败重试，最多 3 次
    return {}  # 全部失败返回空 dict
关键依赖：
  • agent.base_agent.Agent —— 通用 LLM 调用（复用 application 的同款 Agent，不另起炉灶）
  • agent.post.Post.extract_pattern —— 抽 ```json ... ``` 块的正则工具

# 2. 改完 prompt，重跑
python -m eval.run_eval --mode e2e --output after.json

# 3. 对比两个 JSON 的 overall_score

import json
for f in ['before.json','after.json']:
    d = json.load(open(f))
    scores = [r['score']['overall_score'] for r in d['e2e_results'] if r.get('score')]
    print(f'{f}: avg={sum(scores)/len(scores):.2f} (n={len(scores)})')

场景 B · 测试 plan 反思节点对"否定反馈"的处理

python -m eval.run_eval --mode comp \
  --topic "规范驱动开发（SDD）与AGENTS.md的关系及最佳实践" \
  --feedback "这个计划完全不对，我需要的是对比分析SDD与传统开发方法的差异" \
  --expected-intent replan

预期：actual_behavior = replan_then_proceed，且 plan_reflection_score 中 feedback_incorporation 评分反映新 plan 是否真正改写了方向。

场景 C · 调高搜索强度看边际收益

# 默认：2 查询 / 2 循环

# 强化：5 查询 / 10 循环

对比两份报告的 information_coverage / factual_accuracy / summarization_scores 均值——评估"搜索强度-质量"的边际收益。

7进阶：自定义与排错

7.1 加一个新的评分维度

  1. 在 eval/prompts.py 加一套 XXX_JUDGE_INSTRUCTIONS 模板，结尾强制 JSON 结构
  2. 在 eval/judge.py：
    • 加 XxxScore(BaseModel) 评分模型
    • 加 evaluate_xxx(...) 方法（调用 _safe_format + _call + XxxScore(**result)）
  3. 在 eval/evaluator.py：
    • 加 ComponentResult.xxx_score 字段
    • 在 _eval_one_topic_components 末尾追加调用
  4. 在 eval/evaluator.py:format_eval_report 加打印逻辑

7.2 替换 Judge 模型

# 方式 1：环境变量（推荐）
export EVAL_MODEL=qwen3.7-max
python -m eval.run_eval --mode all

# 方式 2：CLI 参数
python -m eval.run_eval --mode all --judge-model qwen3.7-max

7.3 常见错误与排错

现象 可能原因 排查
[Judge] 全部 3 次尝试均失败 Judge LLM 没返回有效 JSON 查 EVAL_MODEL 是否可达；查 prompt 里是否含特殊字符
终端 错误: xxx 但 JSON 里有 error 字段 agent 流水线本身异常 看 logger 输出；用 --mode e2e --topic "..." 复现
报告里 plan_reflection_score 缺失 topic 没配 user_feedback + expected_intent 预期行为，不是 bug
报告里 citation_score 缺失 最终报告太短或没有引用 加 --max-loops 3 让 agent 多查几轮
报告里 plan_query_alignment_score 缺失 agent 没生成 plan（被 plan_status 跳过） 检查 graph 的 plan 节点逻辑

7.4 调试技巧

  • 最小复现：--mode e2e --topic "..." + 单条 topic
  • 只看分数不看 JSON：跑完直接看终端摘要，定位到具体 topic 后再 jq 看 JSON 详情
  • 调 prompt：改 eval/prompts.py 后重跑，只重跑受影响的那一维度（比如只改 CITATION_JUDGE_INSTRUCTIONS，就把 JSON 里 citation_score 单独提取对比）
  • 跑多次取均值：每次跑结果会波动（搜索结果 + LLM 生成 + Judge 评分都有随机性），重要评估建议跑 3 次
